## 1 P0 修复

### B-1 / B-2 / B-4　DATE 列 Scan 进 string

根因确认：`orders.start_date`、`orders.end_date`、`order_pet.stay_date` 是 `DATE`，pgx 返回
`time.Time`，而 `model.Order` / `model.OrderPet` 的对应字段是 `string`，Scan 直接失败。

修法是与管理端保持一致，在 SQL 侧转文本：

| 位置 | 改动 |
| --- | --- |
| `handler/order_handler.go` `ListMyOrders` | `o.start_date::text, o.end_date::text` |
| `handler/order_handler.go` `ListReceivedOrders` | 同上 |
| `handler/order_handler.go` `GetOrderDetail`（owner / sitter 两条分支） | 同上 |
| `handler/order_handler.go` `GetOrderDetail` 宠物子查询 | `op.stay_date::text` |

### B-2 追加　不再把查询故障伪装成 404

`GetOrderDetail` 现在区分两类错误：`pgx.ErrNoRows` 才返回 `30001 order not found`，
其余返回 500 并写日志（`[GetOrderDetail] scan error`），类型错误不会再被 404 掩盖。

### B-5　扫描错误不再静默

`ListMyOrders`、`ListReceivedOrders`、`GetOrderDetail` 的 `continue` 前都加了
`log.Printf("[函数名] scan error: %v", err)`，与管理端 `admin_extra.go` 的惯例一致。
宠物子查询原本忽略 `Query` 错误并在 `nil` rows 上继续循环，现改为判空后再遍历。

### B-3　支付 50001 commit failed

真实根因是两件事叠加：

1. `payments.amount` 上有 `CHECK (amount > 0)`，而机构日单价为 0 时订单金额就是 0，
   插入流水违反约束；
2. 流水插入的错误被 `_ =` 吞掉，事务已进入 aborted 状态，最终只在 `Commit` 上暴露成
   一句没有信息量的 `commit failed`。

修复（`handler/order_handler.go` `PayOrder`）：

- 金额 `<= 0` 走"无需支付"分支：只把订单置为 `confirmed` / `paid`，不写支付流水，`transaction_id` 返回空串；
- 金额 `> 0` 正常写流水，插入失败立即返回 `写入支付流水失败: <真实原因>`；
- `Commit` 失败同样把原始错误带出来并记日志，不再只给 `commit failed`；
- 迁移 `0010_payments_amount_nonneg.sql` 把约束放宽为 `CHECK (amount >= 0)`，
  `serverdb/init.sql` 同步；约束名通过 `pg_constraint` 动态发现，不依赖固定名字，可重复执行。

### 0 元订单的源头治理

- `handler/order_pricing.go` `computeOrderPricing`：机构价格无效时直接返回
  `该机构未设置有效价格，暂时无法下单`，估价与下单共用同一道校验，不会再产生付不掉的订单；
- `handler/admin_handler.go` `AdminUpdateSitterStatus`：**重新上架**（`inactive` / `banned` → `active`）
  前校验价格必须 `> 0`。首次审核通过（`pending` → `active`）不拦，因为申请阶段还没有机构端，
  价格只能审核通过后由机构在"我的店铺"里补。

## 3 `/health` 补 `build_time`

`handler/system_handler.go` 的响应新增 `build_time`（由 `build.ps1` / `build.sh` 的
`-X ...version.BuildTime` 注入）。有了 version + commit + build_time 三元组，就能确定线上跑的到底是哪份代码。

## 4 D-1 / D-2 / D-3 的真相

清单里"服务器行为与仓库代码不一致"的四个观测点，全部是**同一件事**：上一轮的代码改动只留在了工作区，
没有提交到 master，而线上部署用的是工作区构建物。

| 观测点 | 说明 |
| --- | --- |
| `apply-sitter` 要求 `contact_person` / `license_photo_url` | 机构入驻改为资质审核制，这是预期行为 |
| `daily_price` 被忽略、返回 0 | 申请阶段不再写经营配置，审核通过后由机构在"我的店铺"填写 |
| `capacity` 被强制成 1 | 同上，容量走 `PUT /sitter/capacity` 单独调整 |
| 响应没有 `access_token` | 申请不再当场升级角色，登录态不变，所以不发新令牌 |

`/health` 的 `commit` 显示 `bd302b7` 是因为构建时 HEAD 就是它。本轮已把后端代码入库，
下次出包后的 commit 标识即可信。

## 5 需要你在库上执行的一次性数据修正

演示库里唯一上架机构（清单里提到 id=5「cs」）日单价和上门价都是 0，
按新校验它的订单会被拦在下单前。二选一：

1. 用该机构账号登录桌面端，在"我的店铺"填真实价格（推荐，走正常业务流程）；
2. 直接改库：

```sql
UPDATE sitters
   SET daily_price = 80.00, visit_price = 40.00
 WHERE id = 5;
```

改完可用清单 §7 的回归验收顺序复核，关键三步是：

```
GET  /pet-owner/orders            → items 非空，start_date 为 "YYYY-MM-DD"
GET  /pet-owner/orders/:id        → 200，pets[].stay_date 为字符串
PUT  /pet-owner/orders/:id/pay    → 200，payments 有流水
```
