## 二、N-1（P0）余额支付写流水失败

### 根因（与清单猜测一致，但落点是 `channel`）

`0017_wallet.sql` 建表时：

```sql
channel TEXT NOT NULL DEFAULT 'mock'
        CHECK (channel IN ('mock','wechat','alipay','bank','admin'))
```

而余额支付写的是 `channel='balance'`（`order_handler.go` PayOrder）：

```sql
INSERT INTO wallet_transactions (user_id, type, amount, balance_after, channel, ref_type, ref_id, transaction_id, status)
VALUES ($1, 'consume', $2, $3, 'balance', 'order', $4, $5, 'success')
```

修复前实测的底层报错（本轮已复现，测试输出原样）：

```
[PayOrder] 写入钱包流水失败 user=60 order=36 amount=160.00 balance_after=340.00:
ERROR: new row for relation "wallet_transactions" violates check constraint
       "wallet_transactions_channel_check" (SQLSTATE 23514)
```

充值路径写的是 `mock/wechat/alipay`，所以「充值成功、支付失败」——与清单的对照结论完全吻合。

### 修复

1. **迁移 `0019_wallet_channel_balance.sql`（已执行）**
   - 先按「约束定义里含 channel」定位并删除旧 CHECK（不硬编码约束名，换库也能跑）
   - 重新建 `ck_wallet_transactions_channel`：`balance / mock / wechat / alipay / bank / admin`
   - 给 `wallet_transactions.channel` 补注释说明语义

2. **`PayOrder`（`internal/handler/order_handler.go`）**
   - 写流水失败时 `log.Printf` 打出 `user/order/amount/balance_after/err`，并把 `err.Error()` 带回客户端
   - 扣减钱包失败同样带上底层错误
   - **幂等**：`payment_status='paid'` → `409 该订单已支付，无需重复支付`；非 `pending_pay` → `409 当前订单状态不支持支付`
     （订单行在事务内 `FOR UPDATE`，并发重复调用不会扣两次）
   - 余额支付的 `payments.transaction_id` 与流水统一为 `WALLET-PAY-<订单id>`，并在响应里回传

### 验收（自动化，已通过）

`internal/router/order_flow_integration_test.go::TestWalletBalancePay`：

```
充值 500 → 确认到账 500
下单 160 → PUT /orders/:id/pay {"method":"balance"} → 200
钱包 balance=340 / total_consume=160
流水 1 条：type=consume channel=balance ref_type=order ref_id=<订单> amount=160 balance_after=340
再付一次 → 409，余额仍 340（不重复扣款）
```

> 注：迁移已应用到线上库，**旧二进制在余额支付时也不会再撞约束**；
> 但「409 幂等 + 错误信息带底层原因」需要重新发布二进制才生效。

## 三、N-2（P1）公开机构接口下发联系电话

采用清单的**方案 A**（列表 / 详情 / 搜索都下发），没有新增路由，避免前端再适配一套接口。

### 改动

| 位置 | 变化 |
|---|---|
| `internal/model/sitter.go` | 新增 `contact_phone` / `contact_name`；`contact_person` 从 `json:"-"` 改为公开 |
| `internal/handler/sitter_handler.go` | `ListSitters` / `GetSitter` / `SearchSitters` 全部 `LEFT JOIN users u ON u.id = s.user_id`，取 `u.contact_phone`、`u.contact_name`、`s.contact_person` |
| 搜索 SQL | 同时把 `status/name/address/description` 改成 `s.` 限定（联表后 `status` 会歧义） |

返回示例（实测）：

```json
{
  "id": 6, "name": "小满宠物之家",
  "contact_phone": "13800001111",
  "contact_name": "王女士",
  "contact_person": "张三"
}
```

- 机构没填时三项都是空串，前端按清单降级成「站内留言」
- **不返回** `email`、营业执照、身份证等其它信息
- 隐私文档（`docs/13`）已补「机构联系电话对用户可见」的说明与脱敏建议

### 验收（自动化，已通过）

`TestSitterPublicContact`：临时给机构 6 写入联系方式 → 详情 / 列表 / 搜索三处都断言
