## 二、B-6　订单归属口径统一（P0）

### 根因复核

清单判断正确：**同一笔单在「列表」和「详情」里被两套规则判定归属**。
`ListMyOrders` 永远按 `o.owner_id` 查，详情从前按角色分叉，sitter 走 `s.user_id`。
账号 `role=sitter` 且没有机构资料时，`s.user_id` 那一支永远查不到，于是自己下的单详情 404。

### 改动

| 接口 | 文件:行 | 现在的归属条件 |
|---|---|---|
| 详情 | `internal/handler/order_handler.go:498` | `o.owner_id = $2 OR s.user_id = $2` |
| 取消 | `internal/handler/order_handler.go:758` | `owner_id = $3 OR sitter_id = (SELECT id FROM sitters WHERE user_id = $3 ...)` |
| 改期 | `internal/handler/order_extra.go:84`（`actorID`）、`:99-107`（查询） | 同上 OR 组合 |
| 续费 | `internal/handler/order_extra.go:186`、`:197-210` | 同上 OR 组合 |

配套细节：

1. **通知对象不再等于操作者**。改期 / 续费原来把 `c.GetInt64("user_id")` 直接当 `ownerID` 发个人通知；
   现在改成从订单里 `SELECT owner_id`（`order_extra.go:93` / `:196` 的 `orderOwnerID`），
   机构代改期 / 代续费时，个人通知仍然发给真正的主人，机构侧另外收 business 通知。
2. **支付流水可见性**。详情里原来用 `role != "sitter"` 判断是否返回 `payments`，
   但变量 `role` 在一次未完成的改动里已被删除（该文件当时**编译不过**）。
   现在按归属判断：`o.OwnerID == userID` 才返回资金流水（`order_handler.go:569`），
   机构视角看不到用户的支付渠道信息，机构账号看自己下的单仍能看到流水。

> 注意：`SubmitReview` / `RequestRefund` / `ListDynamics` 等「主人动作」**没有**改成 OR 组合。
> 这些接口写入的是 `owner_id`，若允许接单机构通过，会出现「机构给别人的订单写评价 / 发起退款」的越权。
> 它们在 sitter 账号下的失败根因只是 `owner_id = 当前用户` 匹配不上时的口径问题，而 sitter 自己下的单
> `owner_id` 本来就等于自己，不存在 404。

## 三、B-7　列表 `owner_id`（P1）

`ListMyOrders`（`order_handler.go:344`）的 SELECT 补了 `o.owner_id`，Scan 同步补 `&o.OwnerID`，
列顺序与扫描顺序严格一一对应（顺序：`... s.name, COALESCE(u.username,''), o.owner_id, o.sitter_id`）。
同时把 owner 改成 `LEFT JOIN users`：用户异常缺失时订单不该从列表里消失，`owner_name` 用 `COALESCE` 兜底成空串。

列表现在返回：

```json

 "sitter_name":"小满宠物之家","owner_name":"probe_sitter_...","scope":"mine"}
```

## 四、P2 `scope=received` 与 percent 券

### 4.1 订单列表新增 `scope`

```http
GET /api/v1/pet-owner/orders?scope=mine|received&page=1&per_page=20
```

- `mine`（默认）：`o.owner_id = 我`
- `received`：`s.user_id = 我`（机构视角，与 `/sitter/orders/manage` 同源数据，额外带机构名与下单人用户名）
- 其他值 → `400 未知的订单视角: xxx`
- 响应体新增 `scope` 字段，回显本次视角

两种视角共用同一套字段 / 排序 / 分页，商家端可以用一个页面切换「我下的单 / 我接的单」，不再依赖角色分支。

### 4.2 `percent` 券的语义：**减免百分比**

计算代码在 `internal/handler/order_pricing.go:187-191`：

```go
if ctype == "fixed" {
    discountAmount = value
} else {
    discountAmount = subtotal * value / 100   // percent：value 就是减免百分比
}
```

即 `value=99` 表示**减免 99%**（333 元 → 3.33 元），不是 9.9 折。
所以线上券 id=16「睡觉吧孩子，睡觉吧」的效果符合代码，是**演示数据误填**，不是后端算错。

校验现状与本次补充：

| 位置 | 规则 |
|---|---|
| `admin_ops.go:136`（后台建券） | `percent` 必须是 1-100，否则 400 |
| `sitter_coupon.go:70`（机构建券 / 改券） | `percent > 100` 拒绝；`value <= 0` 由 `binding:"gt=0"` 拦住 |
| **迁移 `0018_coupon_percent_range.sql`（本次新增，已在线上库执行）** | 库级约束 `ck_coupons_percent_range`：`type <> 'percent' OR (value > 0 AND value <= 100)`；并给 `coupons.value` 补注释说明语义 |

> 券 id=16 的 `value=99` 本身在合法区间内，**没有被自动改动**。
> 若演示时希望它别「几乎白送」，执行：
> ```sql
> UPDATE coupons SET value = 15 WHERE id = 16;   -- 改为减免 15%
> ```
