# 接口权限口径调整（2026-11-10）

## 1 问题现象

机构账号在机构端维护自己的资料（`PUT /api/v1/sitter/shop/me`）时返回 403：

```json
{"code":20002,"message":"没有访问该功能的权限"}
```

同一账号调用其他 `/sitter/*` 接口（接单、容量、结算）也是 403，但账号在后台看是「已通过审核」的机构。

## 2 根因

### 2.1 角色是签发令牌时的快照

`middleware.JWTAuth` 原来直接把令牌里的 `role` 放进 `gin.Context`，`RequireRole("sitter")` 只认这个值。

机构申请走的是这条链路：

```
owner 提交入驻申请 → sitters.status = pending（users.role 仍是 owner）
                 → 管理员审核通过 → sitters.status = active
                 → 同时 UPDATE users SET role = 'sitter'
```

角色升级发生在**服务端数据库**，而用户手里那张访问令牌（有效期 30 分钟，刷新令牌 7 天）里写的还是 `owner`。
更麻烦的是刷新接口用 `claims.Role` 续签，旧角色会被无限续下去——除非用户主动退出重新登录，
否则机构端整片接口都是 403。这就是「明明审核通过了，改资料却提示权限不足」。

### 2.2 有些机构记录从来没同步过角色

- 后台「机构管理 → 新建机构」（`AdminCreateSitter`）直接往 `sitters` 插记录，不碰 `users.role`；
- 早期数据、手工导入的数据同样只有机构记录没有角色。

这类账号 `users.role = 'owner'`，登录后看到的身份是「主人」，机构端照样 403。

### 2.3 路由把「店铺自助维护」也一刀切关在角色后面

`GET/PUT /sitter/shop/me`、`POST /sitter/shop` 和接单、结算接口挂在同一个 `RequireRole("sitter")` 组里。
但这两类接口性质不同：接单结算要看角色，而「改我自己那条机构记录」应该由**数据归属**决定，
handler 里本来就是 `WHERE user_id = 当前用户`，没有记录返回 404，不存在串号风险。

## 3 改动

### 3.1 鉴权角色以数据库为准（`internal/middleware/jwt.go`）

新增 `loadAccountState`，把原来分散的三次判断合并成一条 SQL：

```sql
SELECT u.status, u.token_invalid_at, u.role::text, u.session_key,
       EXISTS (SELECT 1 FROM sitters s
               WHERE s.user_id = u.id AND s.deleted_at IS NULL
                 AND s.status IN ('active','inactive')) AS has_shop
FROM users u WHERE u.id = $1 AND u.deleted_at IS NULL
```

- 请求次数不增反减：原来「可用性」一次查询 + 管理员会话再一次查询，现在一次拿全；
- `EffectiveRole` 的判定顺序：数据库角色 → 令牌角色兜底 → **名下有在营机构则按 `sitter` 鉴权**；
- `c.Set("role", 有效角色)`，同时保留 `c.Set("token_role", 令牌原始角色)` 方便排查旧令牌。

「名下有在营机构」这个兜底条件，是给 §2.2 那类角色没同步的账号用的：机构记录本身就是能力凭证，
不依赖 `users.role` 是否被正确升级过。`banned` 不算「在营」，封禁账号不会因此拿到机构权限。

### 3.2 刷新令牌换发新角色（`internal/handler/auth_handler.go`）

`Refresh` 签发新令牌前调用 `middleware.EffectiveRole`，角色调整后最多再活一个访问令牌周期。

`Login` / `GetProfile` 回显的角色也统一成有效角色，避免出现「客户端显示未开通机构、服务端却已放行」的错位。

### 3.3 店铺自助维护脱离角色门（`internal/router/router.go`）

```go
// 任何登录用户，handler 按 user_id 定位，没有机构记录就是 404
protected.GET("/sitter/shop/me", handler.GetMyShop)
protected.PUT("/sitter/shop/me", handler.UpdateMyShop)
protected.POST("/sitter/shop", handler.CreateMyShop)
```

接单、容量、定价规则、优惠券、结算等仍然要求 `sitter` 角色。

### 3.4 建机构时同步角色（`admin_sitters.go` / `admin_handler.go`）

- `AdminCreateSitter`：新建时 `status` 为 `active` / `inactive` 就把账号升为 `sitter`；
- `AdminUpdateSitterStatus`：`inactive`（下架）也算拥有资质，与 `active` 一样升级角色。

### 3.5 数据回填（迁移 `0002_sitter_role_backfill.sql`）

```sql
UPDATE users u SET role = 'sitter', updated_at = now()
WHERE u.role = 'owner' AND u.deleted_at IS NULL
  AND EXISTS (SELECT 1 FROM sitters s
              WHERE s.user_id = u.id AND s.deleted_at IS NULL
                AND s.status IN ('active','inactive'));
```

幂等：已升级的账号不再命中，删除机构记录后角色回落到 owner 属于另一条人工路径，本迁移不动。

## 4 验证

`internal/middleware/jwt_role_test.go` 覆盖角色判定与令牌可用性：

| 用例 | 期望 |
|---|---|
| 数据库已是 sitter | sitter |
| 令牌是 owner 快照，名下有在营机构 | sitter |
| 纯主人账号，无机构 | owner（不提升） |
| 数据库角色为空 | 退回令牌角色 |
| 管理员名下挂了机构 | 仍是 admin |
| 账号被禁用 / 令牌早于吊销点 | 不可用 |
| 吊销后一分钟内签发 | 可用 |

```bash
cd server/patnestServer
go build ./... && go vet ./... && go test ./...
```

手工回归（部署后）：

1. 用一个「有 active 机构、`users.role` 仍是 owner」的账号，**不重新登录**直接 `PUT /sitter/shop/me`，应 200；
2. 普通主人账号（无机构）同一个接口应 404 `no shop found`，而不是 403；
3. 普通主人账号访问 `GET /sitter/orders/manage` 仍应 403；
4. 管理员审核通过某个机构后，该机构账号下一次刷新令牌即拿到 `sitter` 角色。

## 5 部署

1. 重新编译 Linux 二进制（`build.ps1` / `build.sh`），产物为 `artifacts/patnest-api`、`artifacts/patnest-migrate`；
2. `db/migrations/` 里带上 `0002_sitter_role_backfill.sql`，`migrate` 容器启动时会自动执行；
3. 走 `install.ps1` 正常升级即可，**不需要**让所有机构账号退出重登：角色在服务端按请求实时解析。
