## 1 现有鉴权分层

| 分组 | 中间件 | 覆盖接口 | 说明 |
|---|---|---|---|
| 公开 | 无 | `/sitters`、`/sitters/:id`、`/sitters/:id/{capacity,addons,reviews}`、`/auth/{register,login,refresh}`、`/health`、`/version` | 只读机构信息，且强制 `status='active'`；返回字段不含联系人、手机号、营业执照 |
| 浏览（browse） | JWT | `/pet-owner/sitters*` | 任何登录用户可读 |
| 主人（owner） | JWT + `RequireRole("owner","sitter")` | 宠物、订单、券、收藏、动态、工单、注销 | 所有查询都带 `owner_id = 当前用户` |
| 机构（sitter） | JWT + `RequireRole("sitter")` | 接单、容量、动态、评价回复、优惠券、结算 | 通过 `mySitterID(user_id)` 反查机构，写操作一律带 `sitter_id` 条件 |
| 机构资料自助 | JWT | `/sitter/shop`、`/sitter/shop/me` | 不校验角色，只按 `user_id` 定位自己的机构记录，没有记录返回 404（见 `docs/18-接口权限口径调整-20261110.md`） |
| 管理（admin） | JWT + `RequireRole("admin")` + `AdminPermission()` | 后台全部 | 内置 `admin` 不受模块权限限制；其余管理员按 `role_permissions` 逐模块开关 |

## 2 本轮收紧的十一项

### 2.1 跨域来源白名单（原来会回显任意 Origin）

`middleware/cors.go` 之前是"有 Origin 就回显 + `Allow-Credentials: true`"，等于任何网站都能发带凭据的跨域请求并读取响应。

现在：只有 `CORS_ALLOW_ORIGINS` 白名单内的来源才拿到跨域许可；不再声明 `Allow-Credentials`（本项目用 Bearer 令牌，不用 Cookie，`auth_handler` 里也没有 `SetCookie`）；不带 Origin 的客户端（桌面端、小程序、服务端调用）照常可用。默认白名单只放本机 vite dev 两个地址，同源部署无需配置。

### 2.2 寄养动态的参与者校验（原来只校验"登录了"）

`GetDynamic` 已有主人校验，但 `ListDynamicComments`、`CreateDynamicComment`、`LikeDynamic`、`UnlikeDynamic` 没有：任何登录用户换个 `dynamic_id` 就能读到别人家宠物的动态内容、昵称和照片，还能往任意动态下刷留言。

新增 `handler/dynamic_access.go` 的 `canAccessDynamic` / `requireDynamicAccess`，四个接口统一按"该单主人 / 承接机构成员 / 动态作者 / 管理员"判定，否则 403。

### 2.3 管理员账号保护（原来同级可以互相接管）

`AdminResetPassword` 之前对任何目标都放行：一个只被授权"用户管理"的管理员，可以直接改掉内置超级管理员的密码，从而完全接管后台。`AdminUpdateUser` 也能任意降级、禁用其他管理员。

新增 `handler/admin_guard.go`：

- 改动 `admin` 角色账号的角色、状态、密码，只有内置 `admin` 账号可以做；
- 不允许把系统里最后一个可用管理员禁用或降级；
- 内置 `admin` 账号本身不可删除、不可彻底删除（原有保护保留，改为引用常量）。

### 2.4 凭据变更后吊销刷新令牌

重置密码、禁用账号、删除账号之后，旧刷新令牌原本还能继续换新的 access token。现在这三条路径（以及退出登录、申请注销、管理员登录换会话键）统一走 `revokeAllSessions(userID)`：刷新令牌逐条置 `revoked_at`，访问令牌靠 `users.token_invalid_at` 一次性作废，与"修改密码"的 `revokeSessionsBefore` 保持同一套判定。

### 2.5 公开接口限流

登录有失败计数和账号锁定，但 `Register` 和 `Refresh` 完全敞开：脚本可以无限建号，也可以拿 `/auth/refresh` 暴力猜令牌。

新增 `handler/rate_limit.go` 的 `ipRateLimit`，按 IP 计数：注册 10 次/小时，刷新 60 次/小时，超限返回 429（`code=42901`）。Redis 未启用时放行，本地开发不受影响。
刷新阈值为什么要留到 60：访问令牌压到 30 分钟之后，一个正常客户端每小时就要刷 2 次；如果现场所有人共用一个出口 IP（校园网、公司 NAT），按 IP 计数会互相误伤。
阈值可用 `REGISTER_RATE_LIMIT` / `REFRESH_RATE_LIMIT` 覆盖——演示期反复注册测试账号很容易撞上默认 10 次，别到答辩现场才发现被自己的限流挡住。

### 2.6 会话即时吊销（禁用/删除/改密后旧令牌立即失效）

访问令牌是无状态 JWT，此前一旦签发，在有效期内谁都收不回：管理员把账号禁用或删除后，对方手里的 token 还能继续用到过期（当时默认 2 小时）；用户点"退出登录"也只是客户端清了本地令牌，服务端那张 token 依旧有效。

迁移 `0013` 给 `users` 加 `token_invalid_at`，中间件在每次请求比对令牌的 `iat`：早于吊销点、或账号已被禁用/软删除，一律 401。相比维护 jti 黑名单，这里只需一次主键查询，代价可控。

统一入口在 `handler/session_revoke.go`：

| 场景 | 调用 | 效果 |
|---|---|---|
| 管理员禁用 / 删除 / 重置他人密码 | `revokeAllSessions` | 刷新令牌全吊销，访问令牌按 `now()` 作废 |
| 退出登录、申请注销账户 | `revokeAllSessions` | 同上，服务端会话真正结束 |
| 自己修改密码 | `revokeSessionsBefore(当前令牌 iat)` | 其它设备要重新登录，**自己这台不会被踢下线** |

两个容易踩的细节：

- 比较留了 1 分钟宽容窗口。登录时会顺手吊销旧会话，若应用时钟比数据库慢几毫秒，刚发出的令牌会被判成"早于吊销点"，表现为登录后立刻 401。窗口对安全几乎无影响（旧令牌最多再活一分钟）。
- 改密码不能用 `now()` 作吊销点，否则用户改完密码自己先被踢。所以用当前令牌的签发时间做分界。
  刷新令牌也按同一时刻过滤（`created_at < 吊销点`）：早于这次登录的会话换不到新令牌，当前这台设备不受影响。若这里不加过滤，"改完密码两小时后突然掉线"会变成静默续期时代最奇怪的 bug。

`expires_in` 也不再写死 7200，改成按实际配置回显（`JWT_ACCESS_TTL_MINUTES`，默认 30 分钟）。有效期能压到这么短，靠的是下一节的客户端静默续期。

### 2.7 机构资料防重复创建

`POST /sitter/shop` 不查重，同一账号可以建出多条机构记录，而 `mySitterID` 取哪条全看排序，会造成"改了 A 却读到 B"。现在已存在未删除记录时返回 409，提示改为编辑。

### 2.8 客户端静默续期（把访问令牌压短的前提）

后端登录时就下发了 `refresh_token`，但两个客户端都没保存它，访问令牌只能被迫设成 2 小时。现在两端都补上了「撞上 401 → 用刷新令牌换一张 → 原请求重放一次」：

| 端 | 位置 | 做法 |
|---|---|---|
| KMP（桌面/Android 共用） | `shared/.../data/api/ApiClient.kt` | 登录改走 `applyAuth(access, refresh, expiresIn)`；8 个 internal 请求封装 + 地图图片 + 图片上传统一调 `shouldRetryUnauthorized(status, usedToken)` |
| 后台管理端 | `src/stores/auth.js`、`src/api/index.js` | `refresh_token` 存 `localStorage.pn_refresh`；响应拦截器 401 时先续期再重放，续期失败才清会话回登录页 |

三个刻意的设计：

- **单飞**：并发请求一起过期时只发一次刷新请求。KMP 用 `Mutex` + 比较"这次请求带出去的令牌"和当前令牌；后台用一个共享的 `refreshPromise`。不这样做的话，桌面端 5 秒轮询一批请求会把 `REFRESH_RATE_LIMIT` 打光，还会让同一批请求各自拿不同令牌互相顶。
- **只重放一次**：重放前的请求会带上 `_pnRetried` 标记 / 只做一次 `shouldRetryUnauthorized`，刷新后仍然 401 就直接报错，不会递归。
- **会话结束时干净退出**：刷新令牌本身失效（超过 7 天、被吊销）时，KMP 触发 `ApiClient.onAuthExpired`，桌面端清会话并把登录框弹出来（`AppRoot.forceLogoutExpired`），不会停在"看着已登录、请求全失败"的状态。

小程序脚手架（`uniapp/`）目前只有默认模板，没有接口层，所以本轮不动；将来接 API 时必须复用同一套续期逻辑，否则要么把 `JWT_ACCESS_TTL_MINUTES` 调大，要么用户每半小时掉线一次。

### 2.9 刷新令牌轮换（rotation）

此前 `/auth/refresh` 只换访问令牌，同一张刷新令牌能用满 7 天。它相当于 7 天有效的密码，一旦泄漏（日志、备份、抓包）就能一直续命，而且服务端无从分辨。

现在每次刷新都签发一张新刷新令牌，并当场把手里这张标记 `revoked_at`：

- 新令牌先入库、旧令牌后作废；吊销语句失败只记日志不回滚，因为新令牌已经发出去了，此时返回失败反而让客户端停在一张注定作废的令牌上。
- 旧令牌再被使用会命中已有的「令牌已被吊销」分支返回 401，不做级联吊销。级联（检测到复用就吊销整条令牌链）是更严格的方案，但会把并发刷新、多标签页这些正常场景误伤成全员掉线，毕设量级下不值得。
- 两个客户端都已跟上：KMP 在 `refreshAccessToken` 里若响应带 `refresh_token` 就替换本地值；后台 `applyAccessToken(access, refresh)` 同理。遇到没实现轮换的旧版后端（响应无该字段）就沿用手里这张，不会把登录态刷没。

**部署约束**：后端与两个客户端必须一起发布。没带轮换逻辑的旧客户端下次刷新会拿已作废的令牌，得到 401 后只能重新登录一次——不会坏数据，但会掉线。

### 2.10 图片上传限流与内容复核

`POST /upload/image` 是站内唯一能把字节写进对象存储并换回公网链接的入口，此前只有 5MB 上限和扩展名白名单。两个补强：

- **按用户限流**：新增 `subjectRateLimit(c, action, subject, limit, window)`，与原有 `ipRateLimit` 同构但计数维度可指定。上传按 `u{user_id}` 计数，默认每小时 60 次（`UPLOAD_RATE_LIMIT` 可调）。这里按 IP 限流没意义：校园网一个出口 NAT 下几十个人会互相挤占，而拿着被盗账号的人反而可以慢慢铺满。
- **magic bytes 复核**：`sniffImageType` 读文件头 12 字节判断真实格式（PNG / JPEG / GIF / WEBP），认不出是图片返回 400；认出但与扩展名不符也返回 400。落盘用的扩展名和 `Content-Type` 一律取嗅探结果，不信任客户端给的文件名。

只信扩展名等于把这个入口当成任意文件的写入口：改名成 `.jpg` 的脚本会被原样存进对象存储并以本站域名的公网链接发出去，站内 `<img>` 加载不了它，但任何人拿到链接都能把它当成本站托管的下载资源。

实现上先 `bufio.Reader.Peek(12)` 再把这个 Reader 直接交给 MinIO，`Peek` 不消费字节，所以不需要回退文件指针。

### 2.11 机构端写操作审计补齐

后台侧操作早有 `writeAudit`（落 `fn_audit`），机构侧只有优惠券三项接入，容量、定价、加购、改资料都是空白。现在统一补齐，动作名沿用 `SITTER_*` 前缀：

| 动作 | 接口 | 位置 |
|---|---|---|
| `SITTER_SET_CAPACITY` | `PUT /sitter/capacity` | `member_ops.go` |
| `SITTER_CREATE_PRICE_RULE` / `SITTER_DELETE_PRICE_RULE` | 定价规则增删 | `member_ops.go` |
| `SITTER_CREATE_ADDON` / `SITTER_UPDATE_ADDON` / `SITTER_DELETE_ADDON` | 加购服务增改删 | `member_ops.go` |
| `SITTER_UPDATE_SHOP` | `PUT /sitter/shop/me` | `sitter_handler.go` |
| `SITTER_CREATE_COUPON` 等三项 | 优惠券 | 此前已有 |

容量和定价要记新值，因为它们是"事后看不出被改过"的字段——数据库里只有当前态，改前的数字不留痕。机构资料更新反过来只记变更了哪几栏：地址、价格这些在业务表里查得到当前值，日志再存一份快照反而容易和后续修改对不上。

`UpdateMyShop` 的 SET 子句是逐字段拼出来的，`changedColumns` 从拼好的串里反推列名，避免在十二个 `if` 分支里各插一行；配套的 `sitter_handler_test.go` 把这个拼接格式钉住，两处一旦走偏测试就红。

## 3 验证方式

```bash
# 1) 未列白名单的来源不应拿到跨域许可
curl -i -H "Origin: http://evil.example.com" http://127.0.0.1:9200/api/v1/sitters | grep -i access-control-allow-origin

# 2) 换个 dynamic_id 读别人的动态留言，应返回 403
curl -i -H "Authorization: Bearer <无关账号令牌>" http://127.0.0.1:9200/api/v1/pet-owner/dynamics/1/comments

# 3) 非内置管理员重置超级管理员密码，应返回 403
curl -i -X PUT -H "Authorization: Bearer <子管理员令牌>" -H "Content-Type: application/json" \
     -d '{"password":"Abc123456@"}' http://127.0.0.1:9200/api/v1/admin/users/1/password

# 4) 注册限流：第 11 次起返回 429
for i in $(seq 1 12); do curl -s -o /dev/null -w "%{http_code}\n" -X POST \
     -H "Content-Type: application/json" -d '{"username":"t'$i'","password":"Abc123456@","phone":"1380000000'$i'","role":"owner"}' \
     http://127.0.0.1:9200/api/v1/auth/register; done

# 5) 会话吊销：管理员禁用某账号后，该账号此前签发的访问令牌应立即 401
curl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer <被禁用账号的旧token>" \
     http://127.0.0.1:9200/api/v1/pet-owner/orders

# 6) 自己改密码后，当前令牌仍可用（吊销点设在本次登录的签发时间，不踢自己）
curl -s -H "Authorization: Bearer <当前token>" -H "Content-Type: application/json" \
     -d '{"old_password":"...","new_password":"..."}' http://127.0.0.1:9200/api/v1/auth/password
curl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer <同一个token>" \
     http://127.0.0.1:9200/api/v1/auth/me

# 7) 静默续期：用登录返回的 refresh_token 换访问令牌，应当 200 且带上 expires_in
curl -s -X POST -H "Content-Type: application/json" \
     -d '{"refresh_token":"<登录返回的refresh_token>"}' http://127.0.0.1:9200/api/v1/auth/refresh

# 8) 用访问令牌（type=access）去刷新，应被拒绝；伪造 issuer 同样被拒
curl -s -o /dev/null -w "%{http_code}\n" -X POST -H "Content-Type: application/json" \
     -d '{"refresh_token":"<访问令牌>"}' http://127.0.0.1:9200/api/v1/auth/refresh

# 9) 轮换：第 7 条刷新后，旧 refresh_token 应立刻失效（401 令牌已被吊销）
curl -s -X POST -H "Content-Type: application/json" \
     -d '{"refresh_token":"<第7条用过的那张>"}' http://127.0.0.1:9200/api/v1/auth/refresh

# 10) 上传内容复核：把任意非图片文件改名成 .jpg 上传，应返回 400 文件内容不是有效的图片
echo not-an-image > /tmp/fake.jpg
curl -s -X POST -H "Authorization: Bearer <token>" -F "file=@/tmp/fake.jpg" \
     http://127.0.0.1:9200/api/v1/upload/image

# 11) 机构端审计：改一次容量，审计日志应有 SITTER_SET_CAPACITY 记录
curl -s -X PUT -H "Authorization: Bearer <机构token>" -H "Content-Type: application/json" \
     -d '{"date":"2026-12-01","capacity":5}' http://127.0.0.1:9200/api/v1/sitter/capacity
curl -s -H "Authorization: Bearer <管理员token>" \
     "http://127.0.0.1:9200/api/v1/admin/audit?action=SITTER_SET_CAPACITY"
```

`go build ./... && go vet ./internal/... && go test ./internal/...` 全部通过；`sniffImageType` 与 `changedColumns` 有配套单元测试。

## 4 已知遗留（按优先级）

| 优先级 | 事项 | 建议 |
|---|---|---|
| 不做 | 每次请求多一次 `users` 主键查询做会话校验 | 刻意保留。加 30 秒缓存会把"禁用/删除即刻生效"退化成最长 30 秒的窗口，正是 §2.6 要消除的东西；主键命中 `SELECT ... WHERE id = $1 AND deleted_at IS NULL` 在毕设量级下开销可忽略，用性能换回语义不划算 |
| ~~中~~ 已完成 | 刷新令牌轮换（rotation） | `/auth/refresh` 每次签发新 refresh 并当场作废旧的（`revoked_at`），被盗令牌最多在被正常客户端下一次刷新前有用。见 §2.9 |
| ~~中~~ 已完成 | `POST /upload/image` 加固 | 按登录用户限流（`UPLOAD_RATE_LIMIT`，默认 60/小时），并用文件头 magic bytes 复核真实类型，与扩展名不符直接 400。见 §2.10 |
| ~~低~~ 已完成 | 登录失败锁定按 `IP + 用户名`，代理层若没透传真实 IP 会被绕过或误伤 | 已 `SetTrustedProxies`（只信 127.0.0.1/::1 与三个内网段），`deploy/nginx/patnest.conf` 与 `deploy/docker/nginx/default.conf` 都已 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`。若将来换网关，需同步检查这两处 |
