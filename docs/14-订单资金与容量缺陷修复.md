# 宠栖 PatNest · 订单资金与容量缺陷修复

> 版本：V1.2 · 2026-11-04
> 范围：下单 / 取消 / 拒单 / 退款 / 超时自动取消 / 续住 / 改期 / 完成 / 后台删单路径上的容量与资金一致性
> 关联：`docs/12-后端权限与限流收紧说明.md`、`docs/02-数据库设计.md`

本轮在权限收紧之后复查订单链路，发现五个会造成实际资损、超卖或账目失真的缺陷，都已修复。
其中第 2 条需要执行迁移 `0014` 才生效。

---

## 1 超时自动取消重复释放容量（会超卖）

`serverdb/init.sql` 里的 `trg_order_cancel_release` 已经在做这件事：

```sql
AFTER UPDATE OF status ON orders
WHEN (OLD.status IS DISTINCT FROM NEW.status)
-- 函数体：pending_pay/confirmed/accepted -> cancelled/rejected 时 fn_release_capacity
```

而 `expireOneOrder`（30 分钟未支付的自动取消）在 UPDATE 之后又手动调了一遍 `fn_release_capacity`，
同一笔订单的占用被减了两次。`used` 有 `GREATEST(...,0)` 兜底不会变负数，
但会把同一天别的在住订单也算成空位：

```
容量 10；订单 A 占 2、订单 B 占 3，used = 5
A 超时取消 -> 触发器减 2（used=3），Go 再减 2（used=1）
此时真实占用是 3，系统却以为只剩 1，还能再塞 9 只 -> 超卖
```

修法是删掉那处手动释放，并在原处留注释说明触发器已经负责。
其余手动调用点都是对的：`AdminUpdateOrder`、`performRefund` 只在 `staying` 时补刀（触发器不管这个态），
`AdminDeleteOrder` 改的是 `deleted_at` 而非状态，触发器不会触发。

顺带把 `expireOneOrder` 里只为那次手动释放而查的 `sitter_id / start_date / end_date / pet_count` 四个列收掉，
免得以后有人照着这几个还在的变量又把释放调用加回来。

## 2 取消订单不退优惠券和积分（迁移 0014）

下单时券被置为 `used`、积分被扣，但取消、拒单、退款、超时取消没有一处把它们退回。
最刺眼的是取消一笔**待支付**订单：用户一分钱没付，却永久损失一张券和一笔积分，且没有任何路径能补救。

退回逻辑放在数据库而不是各 Go 出口，原因是入口有六个（主人取消、机构拒单、后台改状态、
后台退款、超时自动取消、管理员删单），漏一个就是线上事故；放在触发器里与容量释放同一时机，天然全覆盖。

新增 `fn_restore_order_benefits(order_id)`，幂等：

- 券：只处理 `order_id = 本单 AND status = 'used'` 的行，退回后状态变 `unused`，第二次调用自然匹配不到；
  同时 `coupons.used_qty` 减一。先减计数再解绑 `order_id`，否则关联就找不到了。
- 积分：除了 `points_used > 0`，还要求 `points_ledger` 里不存在本单的正向流水，
  回补时写一条 `'订单作废退回'` 的反向流水，账能对得上。

`fn_order_status_changed` 里权益退回的范围比容量释放多一个 `staying`：
住到一半被后台取消，券和积分同样该退；但容量仍只在前三态释放，因为 `staying` 的容量
由后台退款逻辑按已住天数显式处理，在触发器里重复释放等于把已消耗的天数也退成空位。

不在管理员删单（`deleted_at`）时退回：删除一笔进行中的订单是数据纠偏动作，
资金和权益应该走退款流程处理，两条路都退会变成第二次退款。

## 3 下单核销优惠券吞掉错误（可重复用券）

`CreateOrder` 里的核销语句原本写成 `_, _ = tx.Exec(...)`，两处错误被丢弃。
一旦 `UPDATE` 失败（约束冲突、连接中断），事务照常提交，结果是一笔**已经扣了券的钱**配上一张**仍是 `unused` 的券**，
同一张券可以被反复用于下单。

现在两处都判错回滚，并且核销语句自带状态条件 `AND status = 'unused'`：
并发下若这张券已被别的请求核销，`RowsAffected()` 为 0，直接返回 409 而不是继续下单。
与 `computeOrderPricing` 在下单路径上对券行加的 `FOR UPDATE` 配合，这条竞态被封死。

## 4 顺带处理

- `GET /api/v1/version` 不再返回 `go_version`。该端点无需登录，而后台面板只用到
  `version / commit / slot / build_time`；运行时细节登录后的 `/admin/system/info` 里照旧有。
- `updater.readJob` 的任务编号正则提到包级变量 `jobIDRe`，不再每次查询任务状态都重新编译。
  这条正则同时也是 `JobDetail` 拼日志路径时的越界防护，注释里写明了这层用途。

## 5 续住不收款，还把原价覆盖成整段房价

桌面端和接口文档都写着"续住会占用当晚容量并补差价"，但 `RenewOrder` 一分钱都没收到过：
它只往 `payments` 插一条 `status = 'created'` 的待支付流水，而订单的 `payment_status` 仍是 `paid`、
状态也没有退回待支付，那条流水不会被任何流程消费。等于**免费续住**，延长的天数全是机构自己贴的。

同一处还有第二个错误：`total_amount` 被直接赋值成 `computeStayAmount(start, newEnd)`，也就是整段住宿基础价，
原单的加购服务费、优惠券抵扣、积分抵扣在这一步全被抹掉（`estimated_amount` 同样被覆盖）。
后果不止账面数字：后台退款的金额上限取 `total_amount`（`performRefund` 校验 `refundAmount <= total_amount`），
而实际收到过的只有当初那一笔，于是续住过的订单可以按虚高金额全额退回，构成第二次资损。

现在的口径：

1. 差价按**新增的那一段服务**计算：`computeStayAmount(sitter, old_end, new_end, pet_count)`。按天机构逐日累加新增夜间价格并套用节假日上浮；按次机构视为再购买一次服务，收 `visit_price × pet_count`。
2. `estimated_amount` 与 `total_amount` 只在原值上累加这一次差价，加购与优惠保持不动；已住过的天数不因机构调价而重算。这段算术抽成 `renewAmounts`，由 `order_extra_test.go` 钉住不变式（`total_new = total_old + charge`，且续住后金额不得低于原实付）。
3. 差价作为一条 `status = 'paid'` 的流水立即入账，与 `PayOrder` 同口径。本项目是 mock 支付、没有真实网关，改成"先挂账再支付"只会让钱继续收不上来。流水号 `RENEW-YYYYMMDD-<order_id>`，`raw_response` 标 `{"type":"renew_diff"}`，后台订单详情的支付列表里可直接对账。
4. 机构通知带上补收金额；桌面端弹窗写明"按机构当前排期价立即补收差价"、按钮改为"确认续住并补差价"，成功提示显示实收差价；`RenewResult` 增加 `extra_amount` 与 `transaction_id` 字段。

顺带把 `performRefund` 读取原支付信息的那句从"最后一条已支付流水"改成整单已支付流水求和：续住会带来第二条，审计字段 `paid_amount` 应当是该订单真实收到过的总额，`refund_of_payment_id` 仍取最后一笔。

### 改期有同一处错误（一并修正）

`RescheduleOrder` 原本用同一套写法：`total_amount = computeStayAmount(start, end)`。
改期一次，加购服务费与优惠券、积分抵扣同样被从账面上抹掉。现在抽成 `rescheduleAmounts`，
只有住宿基础价的变化进入订单金额；`charge > 0` 且订单已支付时保留原来的拦截提示
（"请先联系平台补差价"），待支付订单则直接按新金额支付。

残留：改到更便宜的档期时 `total_amount` 会低于当初实付，而退款上限按 `total_amount` 校验，
这部分差额目前要管理员在退款时手工指定金额。若要彻底闭环，需要引入"改期差价退回"流水，
与续住差价收取对称。本轮没有改动这个行为，先记在这里作为遗留项。

## 6 下单报 capacity exceeded，但机构明明有空位（迁移 0015）

演示时给机构下单返回 409，文案是一句英文 `capacity exceeded for selected dates`。
用 `cmd/capprobe` 把 `sitter_daily_capacity.used` 与"按有效订单逐日重算"的占用对比，
查出三处叠加的账目错误：

1. **陈旧上限**。`fn_reserve_capacity` 建日容量行时把当时的 `sitters.capacity` 写进行内，
   机构之后改容量这些行不会跟着变；而所有读取处都是 `COALESCE(c.capacity, s.capacity)`——行存在就以行为准。
   于是一次性快照永久伪装成"按日覆盖上限"：线上 67 行里 42 行仍是旧值 1，而机构默认容量是 6。
2. **完成后不释放**。订单进入 `completed` / `evaluated` 时不归还容量。演示里订单常在结束日期之前就被判完，
   那几十天夜间再也还不回去：机构"狗剩"有 39 天被一笔 `evaluated` 订单（11-05 ~ 12-14）占死，
   叠加上一条的上限 1，任何新订单立刻被拒。
3. **软删进行中订单不释放**。后台删单只写 `deleted_at`，容量既不释放，订单又从所有重算口径里消失，
   `used` 变成谁也说不清的残留数（机构 cs 的 11-04 ~ 11-06 就是这么来的）。

处置（全部落在 `0015_capacity_ledger_consistency.sql`）：

- 新增 `is_override`：只有机构用"按日容量"接口显式设置过的日期才算覆盖（`SetDailyCapacity` 写入 TRUE），
  其余跟随机构默认容量；
- 新增 `trg_sitter_capacity_sync`：机构默认容量变化时批量刷新未覆盖的行，覆盖机构自改、后台编辑、直接 SQL 三类写入路径；
- `fn_reserve_capacity` 改成 upsert + `RETURNING`：每次占用都按当前生效上限校验，并顺带回写未覆盖行的容量；
  保留 `ON CONFLICT DO UPDATE` 的行锁，同一天的并发占用仍然串行；
- `fn_order_status_changed` 增加分支：从进行中状态转到 `completed` / `evaluated` 时，归还 `current_date` 之后的夜间；
- 新增 `fn_order_deleted` + `trg_order_deleted_release`：软删进行中的订单时释放容量；
  资金与券仍按 §2 的结论走退款流程，不在此处退回；
- 应用层加了默认容量护栏：机构自改或后台编辑把默认容量调到低于某个未覆盖日期的已占用数时直接 400，
  并指出是哪一天（否则机构会把自己的可订状态改坏，而报错只说当天容量已满）。
- 末尾两条重算语句修平历史账目：未覆盖行的容量回到机构默认值，`used` 一律按有效订单重算
  （判定与下单一致：`start_date <= 该日 < end_date`，累加 `pet_count`）。

0015 已在线上库执行（事务内应用，178ms；执行前用 `cmd/capprobe -dump` 备份了整张容量表）。复查结果：
四个机构 `mismatch_days` 全为 0、陈旧容量行 0；`-reserve` 试占原来被占死的 11-05 ~ 12-14 现在可以占用，
同区间试占 7 只（上限 6）仍然正确拒绝并报出具体日期；`-trigtest` 在事务内模拟"完成"和"软删"，
两处的 `used` 都正确归还，测试整体回滚未落库。

一个必须说明的取舍：历史行无法区分"机构真设过按日覆盖"还是"快照"，0015 一律按快照处理，
所以现在所有日容量行都跟随机构默认容量。若某机构确实需要对个别日期单独收容量，
在机构端重新设置一次即可，新的覆盖会带上 `is_override`，之后不再被系统改写。

## 7 验证情况

已验证：`gofmt -l` 无输出，`go build ./... && go vet ./internal/... && go test ./internal/...` 全部通过。

**未验证：`0014` 这个迁移还没在任何 Postgres 上执行过**（本机 Docker 未启动，也没有本地实例，
而线上库不该拿来做语法试验）。plpgsql 函数体在 `CREATE FUNCTION` 时就会解析，
所以上线前请在测试库先跑一次 `migrate`，确认无报错，再按下面的行为用例走一遍：

```sql
-- 建一张未支付的券+积分订单，取消后应当：券回到 unused、积分退回、多一条退回流水
UPDATE orders SET status = 'cancelled' WHERE id = :order_id;

SELECT status, order_id FROM user_coupons WHERE user_id = :owner_id;      -- 期望 unused / NULL
SELECT points FROM users WHERE id = :owner_id;                            -- 期望回到下单前
SELECT change_amount, reason FROM points_ledger WHERE ref_id = :order_id; -- 期望 -N 与 +N 各一条

-- 幂等性：同一单再触发一次不应重复退（改状态绕回再改回来）
UPDATE orders SET status = 'confirmed' WHERE id = :order_id;
UPDATE orders SET status = 'cancelled' WHERE id = :order_id;
```

续住这条不需要迁移，改动全在应用层，行为用例：取一张 `status = 'staying'` 且 `payment_status = 'paid'` 的订单
调 `PUT /pet-owner/orders/{id}/renew`，应当看到 `payments` 新增一条 `status = 'paid'` 的流水，
且 `total_amount` 的增量等于该流水金额、`estimated_amount` 的增量等于新增夜间房价之和；
原单的 `addon_amount`、`discount_amount`、`points_used` 不应变化。
容量类问题现在可以用 `go run ./cmd/capprobe`（只读对账）、`-reserve`（事务内试占用后回滚）、
`-trigtest`（事务内验证触发器后回滚）三条命令现场复核，不必靠猜。

容量释放那条只能靠行为确认：同一机构同一天放两张单，取消其中一张后，
`sitter_daily_capacity.used` 应当等于另一张单的宠物数，而不是被多减一次。
