> 项目代号：宠栖 PatNest

> 状态：设计稿（待确认后落地）

---

## 1. 背景与现状

当前项目里"像钱包"的能力其实有三套，但都不是真正的**真实货币钱包**：

| 能力 | 实现 | 本质 | 缺什么 |
|---|---|---|---|
| 用户积分 | `users.points` + `points_ledger` | 虚拟积分，100 积分 = 1 元，下单 `points_used` 抵扣 | 不可充值、不可提现、不是真钱 |
| 订单支付 | `PayOrder` + `payments` 表 | **模拟支付**（`method='mock'`，交易号 `PAY-MOCK-...`） | 未接真实微信/支付宝，无"余额"概念 |
| 机构结算 | `sitter_settlements` | 机构收益提现申请，管理员打款 | 仅机构/管理后台可见，非 C 端钱包 |

**本方案目标**：新增一个**真实货币钱包**，支持用户**充值 → 余额支付（可与积分/优惠券组合）→ 流水可查 → （可选）提现**，并在管理后台具备对账与人工调账能力。

---

## 2. 业务模型：钱包 vs 积分 vs 结算

三者并列，互不替代：

- **钱包（wallet）**：真实货币。可充值、可支付、可提现。余额 `balance`、冻结 `frozen_balance`（支付中/退款中）。
- **积分（points）**：虚拟奖励，仅用于下单抵扣（100=1 元），不可提现、不可充值。
- **结算（settlements）**：机构侧收益提现，沿用现有 `sitter_settlements`，本方案**默认不改动**（见 §6 方案 A）。

**下单组合示例**：订单 300 元 = 钱包余额支付 250 元 + 积分抵扣 5 元（500 积分）+ 优惠券 45 元。

---

## 3. 数据库设计（迁移 `0017_wallet.sql`）

金额统一用 `NUMERIC(12,2)`（不用 float）。余额变更必须在事务内完成「改 `wallets` + 写 `wallet_transactions`」，并加行锁/乐观锁防并发超扣。

### 3.1 `wallets` — 每用户一条（机构复用同一表）

```sql
CREATE TABLE IF NOT EXISTS wallets (
    user_id        BIGINT PRIMARY KEY REFERENCES users(id) ON DELETE RESTRICT,
    balance        NUMERIC(12,2) NOT NULL DEFAULT 0,
    frozen_balance NUMERIC(12,2) NOT NULL DEFAULT 0,
    total_recharge NUMERIC(14,2) NOT NULL DEFAULT 0,
    total_consume  NUMERIC(14,2) NOT NULL DEFAULT 0,
    version        BIGINT        NOT NULL DEFAULT 0,   -- 乐观锁
    created_at     TIMESTAMPTZ   NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ   NOT NULL DEFAULT now(),
    CONSTRAINT chk_wallet_balance_nonneg CHECK (balance >= 0),
    CONSTRAINT chk_wallet_frozen_nonneg  CHECK (frozen_balance >= 0)
);
```

### 3.2 `wallet_transactions` — 资金流水（核心对账依据）

```sql
CREATE TABLE IF NOT EXISTS wallet_transactions (
    id             BIGSERIAL PRIMARY KEY,
    user_id        BIGINT       NOT NULL REFERENCES wallets(user_id),
    type           TEXT         NOT NULL CHECK (type IN
        ('recharge','consume','refund','withdraw','settle_in','adjust_add','adjust_sub')),
    amount         NUMERIC(12,2) NOT NULL CHECK (amount > 0),
    balance_after  NUMERIC(12,2) NOT NULL,              -- 服务端计算，绝不让客户端传
    status         TEXT         NOT NULL DEFAULT 'success'
                                    CHECK (status IN ('pending','success','failed')),
    channel        TEXT         NOT NULL DEFAULT 'mock'
                                    CHECK (channel IN ('mock','wechat','alipay','bank','admin')),
    ref_type       TEXT,                              -- order / recharge / withdraw / settlement / admin
    ref_id         BIGINT,
    transaction_id TEXT,                              -- 第三方流水号（回调对账）
    remark         TEXT,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_wtx_user_time ON wallet_transactions (user_id, id DESC);
CREATE INDEX IF NOT EXISTS idx_wtx_ref       ON wallet_transactions (ref_type, ref_id);
```

### 3.3 `recharge_orders` — 充值单（异步回调 / 幂等）

```sql
CREATE TABLE IF NOT EXISTS recharge_orders (
    id             BIGSERIAL PRIMARY KEY,
    user_id        BIGINT       NOT NULL REFERENCES wallets(user_id),
    amount         NUMERIC(12,2) NOT NULL CHECK (amount > 0),
    channel        TEXT         NOT NULL DEFAULT 'mock'
                                    CHECK (channel IN ('mock','wechat','alipay')),
    status         TEXT         NOT NULL DEFAULT 'pending'
                                    CHECK (status IN ('pending','paid','failed','closed')),
    transaction_id TEXT UNIQUE,                       -- 第三方充值流水号，幂等键
    paid_at        TIMESTAMPTZ,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

> 历史库需执行 `0017_wallet.sql` 才会建表；`init.sql` 同步补三张表定义与触发器。

## 4. 后端 API 设计

复用现有分组与中间件：`owner`（含 `RequireRole("owner","sitter")`）、`sitter`、`admin`，均带 `JWTAuth()`。

### 4.1 路由总览

| 方法 | 路径 | 分组 | 说明 |
|---|---|---|---|
| GET | `/pet-owner/wallet` | owner | 钱包概览（余额、冻结、累计充值/消费） |
| GET | `/pet-owner/wallet/transactions` | owner | 流水分页（`type`、`page`、`per_page`） |
| POST | `/pet-owner/wallet/recharge` | owner | 发起充值，返回充值单 + 支付参数 |
| POST | `/pet-owner/wallet/recharge/:id/pay` | owner | **模拟网关**：确认充值（真实网关走回调） |
| POST | `/pet-owner/wallet/withdraw` | owner | 提现申请（见 §9 待确认项，可暂缓） |
| PUT | `/pet-owner/orders/:id/pay` | owner | **改造**：新增 `method` 支持余额支付 |
| POST | `/api/v1/payments/recharge/notify/:channel` | 公开 | 充值异步回调（微信/支付宝） |
| GET | `/admin/wallets` | admin | 钱包列表（关键词/余额排序/分页） |
| GET | `/admin/wallets/:user_id` | admin | 钱包详情 + 流水 |
| POST | `/admin/wallets/:user_id/adjust` | admin | 人工调账（正负皆可，写审计） |
| GET | `/admin/wallet/recharges` | admin | 充值单对账列表 |
| POST | `/admin/wallet/recharges/:id/confirm` | admin | 手动确认充值（模拟网关兜底） |

### 4.2 关键接口契约

**GET /pet-owner/wallet**
```json
{ "code":0, "message":"ok", "data": {
  "balance": 250.00, "frozen_balance": 0.00,
  "total_recharge": 500.00, "total_consume": 250.00
}}
```

**POST /pet-owner/wallet/recharge** 入参 `{ "amount": 100.00, "channel": "mock" }`
```json
{ "code":0, "message":"ok", "data": {
  "recharge_id": 12, "amount": 100.00, "channel": "mock", "status": "pending",
  "pay_params": { "pay_url": "mock://pay/12", "qr": "" }
}}
```

**GET /pet-owner/wallet/transactions?type=consume&page=1&per_page=20**
```json
{ "code":0, "message":"ok", "data": {
  "items": [
    { "id":9, "type":"consume", "amount":250.00, "balance_after":0.00,
      "status":"success", "channel":"balance", "ref_type":"order", "ref_id":88,
      "created_at":"2026-11-05 14:02" }
  ], "total":1, "page":1, "per_page":20
}}
```

**PUT /pet-owner/orders/:id/pay** 入参（在原有基础上新增 `method`）
```json
{ "method": "balance" }   // balance | wechat | alipay | mock（默认 mock，保持兼容）
```

### 4.3 支付网关抽象（可平滑替换真实支付）

```go
// internal/payment/gateway.go
type PaymentGateway interface {
    // 创建支付/充值单，返回给客户端拉起支付的参数（二维码/预支付串等）
    CreateCharge(ref string, amount float64) (payParams map[string]interface{}, err error)
    // 校验异步回调，返回第三方流水号与金额；验签失败返回 ok=false
    VerifyNotify(body []byte, headers map[string]string) (txnID string, amount float64, ok bool, err error)
}
```
- `MockGateway`：同步返回 `pay_url`，`/recharge/:id/pay` 直接置 paid（与现有 `PayOrder` 的 mock 行为一致）。
- `WechatGateway` / `AlipayGateway`：占位实现，需商户号、API 证书、回调公网域名；接入时替换 `gateway` 工厂返回值即可，**业务 handler 不变**。

### 4.4 `PayOrder` 改造要点

1. 解析 `method`；`total_amount` 为订单实付额（已扣积分/优惠券）。
2. `method=balance`：事务内 `SELECT balance FROM wallets WHERE user_id=$1 FOR UPDATE`；校验 `balance >= total_amount`；条件扣减
   `UPDATE wallets SET balance=balance-$1, total_consume=total_consume+$1, version=version+1 WHERE user_id=$2 AND balance>=$1`（受影响行数≠1 → 409 余额不足）；写 `wallet_transactions(type=consume, ref=order)`；写 `payments(method='balance', status='paid')`。
3. `method=wechat/alipay`：写 `payments(status='pending')` + `recharge_orders` 同类思路生成支付单，返回 `pay_params`；回调 `VerifyNotify` 成功后入账（若混合"余额+第三方"，余额部分实时扣、第三方部分回调补扣）。
4. 0 元订单（全额抵扣）保持原「直接 confirmed」逻辑。

## 6. 机构侧钱包策略（二选一，建议 A）

- **方案 A（推荐，范围小）**：机构收益提现继续走 `sitter_settlements`，**本方案不动机构侧**。钱包只服务 C 端用户；机构「我的收益」页面维持现状。
- **方案 B（可选）**：机构也建钱包，`settle_in` 入账、`withdraw` 提现，替换 `sitter_settlements` 流程。工作量大，需单独评估。

> 默认按方案 A 落地，方案 B 作为后续扩展。

## 7. 资金安全与对账要点

- **事务 + 行锁/乐观锁**：余额变更一律事务内 `FOR UPDATE` 或 `version` 乐观锁，杜绝并发超扣。
- **条件扣减**：`UPDATE ... WHERE balance >= amount`，受影响行数校验，不足即 409。
- **流水权威**：`balance_after` 由服务端计算后落库，客户端传值一律忽略。
- **幂等**：充值/支付回调以 `transaction_id` UNIQUE 去重，状态机 `pending→paid` 幂等。
- **金额精度**：全程 `NUMERIC(12,2)`，杜绝浮点误差。
- **审计**：调账、充值确认、提现审核走现有 `writeAudit`（参照 `admin_ops.go` 的 `SETTLE_SITTER`）。
- **限流**：充值/提现接口接入现有 `rate_limit.go` 频率限制，防刷。
- **真实网关**：微信/支付宝回调必须验签，模拟网关仅用于演示，结构上可一键替换。

## 10. 风险与待确认项（确认后开始落地）

1. **真实支付资质**：毕设通常无微信/支付宝商户号。默认 **MockGateway** 可演示；接入真实网关需商户号/证书/公网回调域名，届时仅替换 `gateway` 工厂。
2. **C 端是否开放提现**：建议仅做「退款退回钱包」，不开放主动提现（涉资金出境/合规）。如需提现再补 `withdraw` 审核流。
3. **机构钱包**：默认方案 A（不动），是否需要方案 B 请确认。
4. **充值下限/上限、是否接短信/实人认证**：演示阶段可简化，生产需补。
