# 商家直播功能（2026-11-05）

> 一句话：**机构开播 → 用户观看 → 平台审核**。
> 音视频走自建 SRS（RTMP 推 / HLS·HTTP-FLV 拉）。**开播由 App/桌面端自己采集摄像头与麦克风直接推流**
> （Android：RootEncoder；桌面：JavaCV/FFmpeg），不依赖 OBS；后端负责直播间、在线人数、弹幕与封禁。

---

## 一、能力矩阵

| 端 | 开播 | 观看 | 弹幕 | 审核 / 封禁 |
|---|---|---|---|---|
| 机构 App / 桌面端 | ✅ 软件内直接开播（摄像头 + 麦克风 → RTMP） | ✅ 内嵌播放器看别人的直播 | ✅ | — |
| 小程序（uniapp） | —（只读） | 接口已通，页面由小程序端自行接入 | 接口已通 | — |
| 管理后台 | — | ✅ 列表 / 详情 / 拉流地址 | ✅ 隐藏违规弹幕 | ✅ 强制下播 / 封禁机构 / 解封 |

> 说明：App/桌面端「开播」= 创建直播间拿到 `push_url`，随后**由客户端自己采集摄像头 + 麦克风做
> H.264/AAC 编码并推 RTMP**（Android 用 RootEncoder 的 `RtmpCamera2`，桌面用 JavaCV/FFmpeg）。
> 外部推流工具（OBS 等）只是备选，不是必需。

## 二、架构

```
机构 App/桌面端（摄像头+麦克风） --RTMP:9201--> SRS --HLS:9202--> 小程序 <video>
                                                     --HTTP-FLV:9202--> App / 桌面（内嵌播放器）
后端 :9200  ← 直播间/弹幕/封禁 HTTP API
```

- **推流凭证** = `live_rooms.stream_key`（12 字节随机 hex）。只有开播接口和后台详情会下发它；
  观看端拿到的 `LiveRoom` 里 `stream_key` / `push_url` 恒为空。
- **在线人数**：`live_viewers` 表 + 90 秒滑动窗口。客户端进房后每 30 秒 `POST /live/:id/join` 当心跳，
  `total_views` 只在首次进房 +1。
- **封禁**：封在机构上（`sitters.live_banned_at`），同时把该机构所有 `living` 直播间置为 `banned`。

## 三、数据表（迁移 `0020_live_streaming.sql`）

| 表 | 用途 | 关键约束 |
|---|---|---|
| `live_rooms` | 一场直播 | `status ∈ living/ended/banned`；**同一机构只能有一个 living**（部分唯一索引） |
| `live_viewers` | 在线观众 | `(room_id,user_id)` 主键，`last_seen_at` 90s 窗口 |
| `live_messages` | 弹幕 | `status ∈ visible/hidden`，后台可隐藏 |
| `sitters.live_banned_at` / `live_ban_reason` | 直播封禁 | 非空即禁止开播 |

## 四、接口

### 4.1 观看端（任何登录用户）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/live?page=&per_page=&sitter_id=` | 直播中列表（含 `play_hls/play_flv`，不含推流钥匙） |
| GET | `/api/v1/live/:id` | 直播间详情（结束后仍可查，用于回显结束原因） |
| POST | `/api/v1/live/:id/join` | 进房 **兼心跳**（30s 一次），返回最新在线人数 |
| POST | `/api/v1/live/:id/leave` | 离开 |
| GET | `/api/v1/live/:id/messages?after_id=` | 拉弹幕（`after_id` 增量拉取，最多 100 条） |
| POST | `/api/v1/live/:id/messages` | 发弹幕，`content` 1~200 字 |

`LiveRoom` 主要字段：

```json
{
  "id": 4, "sitter_id": 13, "sitter_name": "小满宠物之家",
  "title": "今天带大家看看寄养房间", "cover_url": null,
  "status": "living", "viewer_count": 3, "peak_viewers": 8, "total_views": 21,
  "started_at": "2026-11-05T16:01:30+08:00", "ended_at": null,
  "end_reason": null, "ban_reason": null,
  "play_hls": "http://192.168.3.100:9202/live/<key>.m3u8",
  "play_flv": "http://192.168.3.100:9202/live/<key>.flv",
  "play_rtmp": "rtmp://192.168.3.100:9201/live/<key>"
}
```

### 4.2 机构端（role=sitter）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/sitter/live` | 当前直播 + 最近 20 场历史 + `live_banned/ban_reason` |
| POST | `/api/v1/sitter/live` | 开播，`{title, cover_url}` → 返回 `stream_key/push_url/play_*` |
| PUT | `/api/v1/sitter/live/:id/stop` | 下播 |

错误：已被封禁 → `403 直播权限已被封禁：<原因>`；已有直播 → `409 已有正在进行的直播，请先下播`。

### 4.3 后台（admin）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/admin/live?status=&keyword=` | 全部直播（living 优先），含推流地址 |
| GET | `/api/v1/admin/live/:id` | 详情 + 弹幕（含 hidden）+ 机构封禁状态 |
| PUT | `/api/v1/admin/live/:id/stop` | 强制下播，`{reason}` 选填，通知机构 |
| PUT | `/api/v1/admin/live/:id/ban` | 封禁机构直播，`{reason}` 必填，终止当前直播并通知 |
| PUT | `/api/v1/admin/sitters/:id/live-ban` | `{banned:false}` 解封；`{banned:true,reason}` 封禁 |
| PUT | `/api/v1/admin/live-messages/:mid/hide` | `{hidden:true/false}` 隐藏/恢复弹幕 |

后台操作全部写审计：`LIVE_ADMIN_STOP` / `LIVE_BAN_SITTER` / `LIVE_UNBAN_SITTER` / `LIVE_MESSAGE_MODERATE`。
权限项：`lives.manage`（迁移 0020 已写入 `role_permissions`）。

### 5.3 机构开播步骤

**软件内开播（默认方式）**

1. 机构端「开播」→ `POST /api/v1/sitter/live`，拿到 `room.push_url`
2. App/桌面端进入开播页：
   - Android：`LiveBroadcaster(rtmpUrl)` 自动申请相机/麦克风权限并开始推流（预览即推流画面）
   - 桌面：`CameraBroadcastPanel(rtmpUrl)` 用本机摄像头采集 + 推流 + 预览
3. 观看端 4~10 秒后出画面（HLS 切片 2s）
4. 结束：离开页面自动停推；再调 `PUT /sitter/live/:id/stop`

**备选：外部推流工具（OBS）**

如果临时用其他设备推流，把 `push_url` 拆成「服务器 + 串流密钥」填进工具即可：
服务器 `rtmp://<host>:9201/live`，串流密钥 `<stream_key>`。

## 九、踩坑记录：Android 推流「连接失败：Error configure stream」

真机开播时报：

```
No interface method writeByte(Lkotlin/coroutines/Continuation;)Ljava/lang/Object;
in class Lkotlinx/coroutines/io/ByteWriteChannel; ...
declaration of 'io.ktor.utils.io.ByteWriteChannel' appears in base.apk!classes17.dex
```

**不是业务代码的问题，是依赖版本打架。** RootEncoder `2.5.5` 的 `common` 是按
`io.ktor:ktor-network:2.3.13` 编译的（见其 pom），而本项目自带的 HTTP 客户端是 Ktor `3.6.1`
（Gradle 取高版本，最终落到 classpath 上的是 3.6.1）。Ktor 3 把 `writeByte` 从
`ByteWriteChannel` 的接口方法改成了扩展函数，于是 `RtmpClient` 里编译期的
`invokeinterface ... writeByte` 在运行时找不到目标方法，`connect()` 直接抛异常 ——
表现为预览黑屏 + 「连接失败」。

处理：

1. `rootencoder` 升到 `2.6.6`（编译期 Ktor 3.3.2，与原生的 3.x `ByteWriteChannel` 对齐）；
2. 仍在 `LiveBroadcaster` 里显式 `getStreamClient().setSocketType(SocketType.JAVA)`，
   让 RTMP 走 JDK 原生 Socket，从此不再依赖库与项目两侧 Ktor 版本一致。

顺带修正一处参数误用：`prepareVideo` 的 **5 参重载是 `(w,h,fps,bitrate,rotation)`**，
没有 `iFrameInterval` 的位置，原先写 `prepareVideo(1280,720,30,2_500_000,2)` 等于把旋转角设成 2°。
要设关键帧间隔必须走 6 参重载：`prepareVideo(1280, 720, 30, 2_500_000, 2, 0)`。

## 十、下播后的状态清理（避免「重新进入还在用上一场」）

直播状态是**一份本地缓存 + 服务端事实**，之前只靠本地清，出现四类问题：

| 现象 | 原因 | 处理 |
|---|---|---|
| 下播后重进，仍停在推流页 / 还显示旧推流地址 | `stopLive` 只要接口报错就直接 `catch` 返回，`broadcastRoom` 不清。而后端对已结束的场次回 **409**（后台强制下播、上一次请求其实成功只是响应丢了） | 下播后**无论如何都复核一次** `/live/my`：服务端没有这一场 living 就当作成功，本地收摊 |
| 重进后显示「你还有一场直播在进行」 | `loadMyLive()` 有永久缓存（`myLive != null` 就 return），进页面用的是非强制加载 | 进页面统一走 `reconcileLive()`，直接请求服务端 |
| 离开页面（推流断了）再进来，自动接着上一场推 | 本地 `broadcastRoom` 不和服务端对账，页面看到有 `push_url` 就直接挂 `LiveBroadcaster` | 进页面先对账；若这一场仍在 living，显示**「继续推流 / 结束这场直播」**卡片，用户选了才推 |
| 下一场沿用上一场的标题/封面；换账号还能看到上一个人的场次 | 表单 state 没清；`clearSession` 没清直播状态 | 场次结束后清表单；退出登录清 `liveRooms / myLive / broadcastRoom / liveRoom / 弹幕` |

另外把**列表进房**改成 `nav.openLive(room)` → `enterLiveRoom(room)`：先用列表里的房间立刻出画面，
同时清掉上一间的弹幕与人数，再异步拉一次最新状态 —— 否则「看完 A 再进 B」会先闪一屏 A 的内容。

直播状态机现在只有三个入口：`startLive`（本页开的，直接推）、`reconcileLive`（进页面对账）、
`stopLive`（下播，失败也以服务端事实为准）。任何一处都不再直接改 `broadcastRoom`。

## 十一、延迟优化（2026-11-05）

端到端延迟 = 采集编码 + 网络 + SRS 切片/转发 + 播放器缓冲。默认配置已按「能看且尽量实时」调过：

| 环节 | 配置 | 目标延迟 |
|---|---|---|
| SRS HLS | `hls_fragment 1` / `hls_window 6` / `hls_dispose 30` | HLS **2-3s**（原 2s 切片时 4-6s） |
| SRS 转发 | `gop_cache off` / `queue_length 5` / `mw_latency 100` | 不攒 GOP、队列更短 |
| 推流端 | 桌面 FFmpeg `gopSize = fps`（1s 一个关键帧） | 新观众最多 1s 出画 |
| App / 桌面观看 | 优先 HTTP-FLV：`room.lowLatencyUrl` | **1-2s** |
| 后台 H5 | hls.js：`lowLatencyMode` + 2 段起播 + 1.5× 追帧 | **2-3s** |
| Android | ExoPlayer `targetOffsetMs = 1200`、1s 缓冲、0.95~1.08× 追帧 | 比默认 3 段起播快 1-2s |
| 桌面 VLC | `--network-caching=600 --drop-late-frames --clock-jitter=0` | **1-1.5s** |

调优旋钮：

- **想更实时**：HLS 切片已到 SRS 下限 1s；再往下只能换 HTTP-FLV（App/桌面，已支持）或上
  WebRTC（SRS `rtc_server` + WHEP，可到 1s 内，需要客户端支持；小程序用不了）。
- **网抖明显**：Android `lowLatencyMs` 调 2000、VLC `cachingMs` 调 1200，用延迟换稳定。
- **HLS 压力**：1s 切片意味着每秒一个 ts 请求，SRS/反代压力约是 2s 切片的两倍，演示规模没问题。

> 延迟和「不卡」是跷跷板；现场网络差时优先保证不卡，宁可多 1-2s。

## 十二、画面错乱修复（2026-11-05）

现象：进直播间画面正常一两秒后闪没/黑屏，或者切台后停在上一个直播间的画面。

三个根因，都在「房间对象被整份替换」上：

| # | 位置 | 问题 | 修复 |
|---|---|---|---|
| 1 | 后端 `JoinLiveRoom` | `hideStreamKey` 在 `fillLiveURLs` 之前：play 地址依赖 `stream_key`，先抹掉就拼不出 `play_hls/play_flv`，join 返回的房间**没有任何播放地址** | 改成先 `fill` 再 `hide`，与列表/详情一致 |
| 2 | App/桌面端 `joinLive` | 心跳每 30s 一次，直接把 `viewingLive/liveRoom` 整份替换成 join 返回值；一旦字段缺失（旧服务端、或上面那个 bug），播放器 url 变 null → 拆掉播放器、停上一帧 | 只合并会变的字段（状态/人数/结束原因），**播放地址沿用本地这份**，并用 `fresh.xxx ?: current.xxx` 兜底；心跳回来是别的房间则忽略 |
| 3 | 后端 | 直播被后台下播/封禁后 join 返回 409，客户端原来静默吞掉，画面停在最后一帧 | 捕获「已结束/封禁」，本地把房间置为 ended，播放器随之停止并显示结束提示 |

后台管理页另修了一处：直播详情弹窗关闭时销毁 hls 实例并清掉 `<video src>`，
否则上一场的实例还在后台拉流，下次打开会先闪上一场的画面。

回归用例已补：`TestLiveFlow` 断言 join 返回的 `room` **必须有 play_hls/play_flv、且不能带推流钥匙**。
（演示库里可能同时有人在播，用例改为按房间 id 定位，不再假设列表只有一场。）

## 十三、小程序开播（2026-11-05 调整）

小程序能看直播、但开不了播，分两层原因：**平台限制**（微信侧）和**后端鉴权**（本次已改）。

### 13.1 后端改了什么

| 问题 | 改法 |
|---|---|
| `GET/POST /sitter/live`、`PUT /sitter/live/:id/stop` 挂在 `RequireRole("sitter")` 下。机构审核通过后，小程序里那张旧 token 的 role 仍可能是 `owner`（30 分钟有效期内），一直 403 | 三个接口改到 `RequireRole("owner","sitter")` 的分组，**按机构资料鉴权**，不再看 JWT 的 role |
| 只要名下有机构资料就能开播，待审核/被下架的机构也能推流 | 开播前校验 `sitters.status = 'active'`，否则 403 并给出具体原因（审核中 / 被驳回 / 已下架） |
| 客户端只能靠 403 猜原因 | `GET /sitter/live` 增加 `sitter_status` 与 `can_broadcast`，小程序可直接禁用按钮并显示原因 |

### 13.2 小程序侧必须满足的微信限制

1. **推流只能用 `<live-pusher>` 组件**，且小程序类目需具备「直播」权限（如 社交-直播 / 电商平台 等）；
   没有资质的号，组件不可用，后端改什么都没用。
2. `<live-pusher>` 的 `url` 必须是 **`rtmp://`**，直接用 `POST /sitter/live` 返回的 `push_url`。
3. 开发者工具不支持 `live-pusher`，必须**真机调试**；部分机型需要授权摄像头/麦克风。
4. 观看端 `<live-player>` 同样需要类目；只想看不想开播的小程序可以继续用 `<video>` 播 HLS。

### 13.3 接入顺序（小程序）

```js
// 1) 进开播页先查门禁
const info = await api.get('/sitter/live')        // { can_broadcast, sitter_status, current }
if (!info.can_broadcast) return showTip(info.sitter_status === 'pending' ? '资料审核中' : '暂无开播权限')

// 2) 创建直播间，拿推流地址
const room = await api.post('/sitter/live', { title: '今天带大家看寄养房间' })
// room.push_url = rtmp://<host>:9201/live/<stream_key>

// 3) 用 live-pusher 推流
```

```html
<live-pusher
  url="{{pushUrl}}"
  mode="HD"
  autopush
  enable-camera
  enable-mic
  bindstatechange="onPushState"
  binderror="onPushError" />
```

```js
Page({
  data: { pushUrl: '' },
  async onLoad() {
    const room = await api.post('/sitter/live', { title: '...' })
    this.setData({ pushUrl: room.push_url })
    this.roomId = room.id
  },
  async onUnload() {
    // 4) 下播：停推 + 通知后端
    await api.put(`/sitter/live/${this.roomId}/stop`)
  },
})
```

> 推流成功后，观看端 2-3s（HLS）或 1-2s（FLV）能看到画面。
> 若 `live-pusher` 一直 `error`，先确认类目与真机环境，再看 SRS 是否收到流：
> `curl -s http://127.0.0.1:1985/api/v1/streams`。
