# 宠栖 PatNest · 主人端缺失接口清单

> 版本：V1.0 · 2026-11-02
> 用途：记录**小程序（主人端）在实现过程中发现、但后端尚未提供**的接口。
> 每条给出：缺失原因、小程序端当前替代方案、建议的接口契约（可直接落地）。
> 关联：`docs/03-接口文档.md`（后端 API 规范）、`docs/11-后端问题处理结果.md`（本清单各条的处理结论）

> ⚠️ 本清单里的接口**后端均未实现**。小程序端要么做了本地兜底，要么隐藏了入口，
> 保证演示期不出现「点了没反应」。

## P0 · 阻塞核心体验

### 1. 下单前费用预估

| 项 | 内容 |
|---|---|
| 缺失接口 | `GET /api/v1/pet-owner/sitters/:id/estimate` |
| 期望入参 | `start_date`、`end_date`、`pet_ids[]`、`addon_ids[]`、`user_coupon_id`、`points_used` |
| 期望出参 | `{ estimated_amount, discount_amount, points_discount, addon_amount, total_amount, total_days, breakdown[] }` |
| 缺失原因 | 《03-接口文档.md》只有「下单后返回 `estimated_amount`」（§4.1）；附录 A 的计费纯函数只存在于 Go 代码里（`order_handler.go:55-190`），未暴露 HTTP 端点 |
| 小程序端现状 | `utils/estimate.js` 在本地按后端同口径复算（含 per_day / per_visit、加购、优惠券、积分抵扣），下单页展示「费用明细」并标注**「最终金额以服务端核算为准」** |
| 不做的后果 | 节假日上浮（`sitter_pricing_rules.multiplier`）前端无法复现，费用明细可能与服务端不一致，用户下单前拿不到准确报价 |
| 优先级 | **P0**（角色说明《七》P0 项：费用明细预览） |

### 2. 订单列表按状态分组筛选

| 项 | 内容 |
|---|---|
| 缺失接口 | `GET /api/v1/pet-owner/orders?status_filter=a,b,c`（多状态） |
| 现状 | 后端 `status_filter` 是**单状态精确匹配**（`order_handler.go:345`），传 `confirmed,accepted` 匹配不到任何记录 |
| 小程序端现状 | 订单页**拉全量后在前端分组**（待支付 / 进行中 / 已完成 / 已取消），标签页切换零延迟 |
| 不做的后果 | 数据量上来后客户端要拉全量才能分组，分页语义会错乱 |
| 优先级 | **P0** |

### 3. 订单详情的评价 / 动态 / 支付流水

| 项 | 内容 |
|---|---|
| 缺失能力 | `GET /pet-owner/orders/:id` 的 `OrderDetailResponse` 只赋了 `Order` 与 `Pets`；`dynamics`/`review` 因 `omitempty` 永不出现，`payments` 字段根本不存在（`model/order.go:68-73`；`order_handler.go:479`） |
| 小程序端现状 | 详情页**并发补拉** `GET /orders/:id/review`、`GET /orders/:id/dynamics`、`GET /pet-owner/refunds` 三处 |
| 建议 | 在 `OrderDetailResponse` 里补齐 `dynamics` / `review` / `payments`（`payments` 可给主人看自己的支付与退款流水） |
| 优先级 | **P0**（减少 3 次往返） |

## P1 · 影响体验完整性

### 4. 单条寄养动态详情

| 项 | 内容 |
|---|---|
| 缺失接口 | `GET /api/v1/pet-owner/dynamics/:id` |
| 缺失原因 | 路由表里只有 `GET /pet-owner/dynamics`（列表）、`GET /pet-owner/dynamics/:id/comments`（留言） |
| 小程序端现状 | 动态详情页带 `order_id` 进入，先调 `GET /orders/:id/dynamics` 再从数组里定位该条；若缺 `order_id` 则只展示留言区 |
| 建议 | 直接返回单条动态对象（含 `order_no`、`sitter_name`） |
| 优先级 | **P1** |

### 5. 宠物免疫证明的核验状态回读

| 项 | 内容 |
|---|---|
| 缺失能力 | `model.Pet` 不含 `vaccine_urls` / `vaccine_status` / `vaccine_note`，`ListPets` / `GetPet` 的 SELECT 也没有这几列（`model/pet.go:5-22`；`pet_handler.go:29,137`） |
| 后果 | 主人上传接种证后**看不到平台是否已核验**；管理员核验结果也传不回小程序 |
| 小程序端现状 | 宠物列表不展示核验状态；宠物档案页上传后本地标记为「待核验」 |
| 建议 | 在 `model.Pet` 补 3 个字段并在 SELECT 中带上（数据库列已存在，见 `migrations/0003_admin_extensions.sql:16-17`） |
| 优先级 | **P1**（角色说明《七》P0 项：免疫证明核验闭环） |

### 6. 机构评价的完整列表与分页

| 项 | 内容 |
|---|---|
| 现状 | `GET /sitters/:id/reviews` 硬编码 `LIMIT 20`、无 `total`、无分页，且**不返回** `order_id` / `owner_photos` / `sitter_id`（`sitter_lists.go:15-49`） |
| 小程序端现状 | 机构评价页最多展示 20 条并给出各维度均分聚合 |
| 建议 | 支持 `page`/`per_page`，返回 `total`，并附 `order_id` 供跳转订单 |
| 优先级 | **P1** |

### 7. 宠物历史寄养记录

| 项 | 内容 |
|---|---|
| 缺失接口 | `GET /api/v1/pet-owner/pets/:id/stays`（按宠物维度聚合历史订单） |
| 缺失原因 | 目前只能从订单列表反推，宠物维度的「历史寄养记录」在角色说明《2.1》里被明确要求 |
| 小程序端现状 | 宠物卡片不展示历史次数 |
| 优先级 | **P1** |

## P2 · 增强项

### 8. 距离排序与距离筛选

| 项 | 内容 |
|---|---|
| 现状 | `GET /sitters` 只支持 `type` / `price_min` / `price_max` / `sort`（`price_asc`/`price_desc`/`newest`），**没有** `latitude`/`longitude`/`distance_max` |
| 文档 | §3.1 写了 `distance_max` 与「配合当前经纬度查询」，源码未实现 |
| 小程序端现状 | 排序项只保留「综合推荐 / 价格 / 最新」，**去掉了「离我最近」**，避免点了没反应 |
| 建议 | 后端补 `latitude`/`longitude` 入参 + `sort=distance`（Haversine） |
| 优先级 | **P2** |

### 9. 语义智能推荐（pgvector）

| 项 | 内容 |
|---|---|
| 缺失接口 | `GET /api/v1/pet-owner/sitters/recommend?q=能收胆小的猫` |
| 缺失原因 | 角色说明《2.2》要求「基于 pgvector 语义匹配」，接口文档与路由表均无对应端点 |
| 小程序端现状 | 未实现入口 |
| 优先级 | **P2** |

### 10. 订阅消息（微信 subscribe-message）

| 项 | 内容 |
|---|---|
| 缺失能力 | 后端 `notification_push_tasks.channel` 支持 `wechat` 通道，但**演示环境是模拟通道**，不下发真实订阅消息（§12.12） |
| 后果 | 新动态 / 订单状态变更无法触达用户离线端 |
| 小程序端现状 | 演示期用**站内消息中心**兜底（`GET /notifications`），并在 `docs/03-接口文档.md` §12.12 记录该限制 |
| 建议 | 需先完成小程序主体认证 + HTTPS 合法域名 + 订阅消息模板配置 |
| 优先级 | **P2** |

### 11. 真实支付（微信支付 / 支付宝）

| 项 | 内容 |
|---|---|
| 现状 | `PUT /pet-owner/orders/:id/pay` 是 **mock 支付**，直接置 `paid` 并写一条 `PAY-MOCK-*` 流水（`order_handler.go:507-545`） |
| 缺失能力 | 生成支付二维码/预支付单、支付回调、结果轮询 |
| 小程序端现状 | 详情页「立即支付」直接调 mock 端点，页面明确标注模拟支付 |
| 优先级 | **P2**（个人主体无微信支付资质，演示环境保持 mock） |

### 12. 机构联系信息的直接返回

| 项 | 内容 |
|---|---|
| 现状 | `GET /sitters/:id` 不返回电话/微信等联系方式；只能通过 `POST /pet-owner/sitters/:id/contact` 留言，机构在**机构端**看到 |
| 小程序端现状 | 详情页「联系」按钮走留言通道，会给机构发一条 `system_announcement` 通知 |
| 优先级 | **P2** |

## 三、非接口类的后端缺口

| # | 缺口 | 说明 | 优先级 |
|---|---|---|---|
| A | 订单列表不返回 `sitter_id` | SELECT 未取该列，前端无法从列表跳转机构详情（只能靠 `sitter_name` 展示） | **P0** |
| B | 动态 / 评价接口缺归属校验 | `GET /orders/:id/dynamics`、`GET /orders/:id/review` 未校验订单归属，可越权读取 | **P0**（安全） |
| C | `staying` 状态无写入路径 | 枚举存在但没有任何处理器写入，寄养中状态实际缺失 | **P1** |
| D | 宠物档案无「归档」能力 | 角色说明《2.1》提到「编辑/删除/**归档**」，后端只有软删除 | **P2** |
| E | 优惠券可用范围查询 | 下单页目前拉全量券在前端过滤门槛，无法按机构/品类筛选可用券 | **P2** |
