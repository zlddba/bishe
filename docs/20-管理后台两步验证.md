# 20 - 管理后台两步验证（TOTP）

> 迁移：`serverdb/migrations/0023_admin_totp.sql`（全新库已内联进 `init.sql`）
> 后端：`internal/totp`、`internal/handler/admin_totp.go`、`auth_handler.go`
> 前端：`views/SecurityView.vue`、`views/LoginView.vue`、`views/UsersView.vue`

## 1. 要解决的问题

后台账号一旦密码泄露，攻击者可以直接登录并拿到全部业务数据、退款权限和热更新能力。
仅靠"密码足够复杂"不现实：管理员可能在浏览器里保存密码、在聊天工具里传密码。

两步验证（2FA）在密码之外再加一道**动态口令**：口令由手机上的验证器 App 每 30 秒
重新生成，不经过网络传输，因此即使密码被抓包、被撞库，没有那台手机也进不来。

## 2. 技术选型

| 方案 | 结论 |
|---|---|
| 短信验证码 | 需要短信通道与费用，且换号 / 无信号即锁死，不适合作为后台强制项 |
| 邮件验证码 | 依赖邮箱可达性，延迟不可控 |
| **TOTP（RFC 6238）** | **采用**。离线生成、不产生费用、所有主流验证器（Google / Microsoft Authenticator、1Password、Authy、Bitwarden）都支持 |

实现上**没有引入任何第三方库**：`internal/totp` 用标准库 `crypto/hmac` + `crypto/sha1`
实现 RFC 4226（HOTP）与 RFC 6238（TOTP），参数是业界默认的 `SHA1 / 6 位 / 30 秒`，
因此不存在"某款 App 扫码后码对不上"的兼容问题。

## 3. 数据模型（0023）

`users` 增四列：

| 列 | 类型 | 说明 |
|---|---|---|
| `totp_secret` | `VARCHAR(64)` | base32 密钥。绑定流程一开始就写入，但只有 `totp_enabled=true` 才校验 |
| `totp_enabled` | `BOOLEAN` | 是否已启用。只有提交过一次正确口令才置真 |
| `totp_confirmed_at` | `TIMESTAMPTZ` | 启用时间，后台展示用 |
| `totp_last_step` | `BIGINT` | 最近一次校验通过的时间步（unix 秒 / 30），用于**拒绝同一口令重放** |

新增表 `totp_recovery_codes`：

| 列 | 说明 |
|---|---|
| `user_id` | 所属账号，级联删除 |
| `code_hash` | 恢复码的 sha256，**库里不存明文** |
| `used_at` | 核销时间，`NULL` 表示未使用 |

唯一索引 `(user_id, code_hash)` 防重复，部分索引 `WHERE used_at IS NULL` 支撑"还剩几枚"的查询。

> 为什么 `totp_secret` 存明文：它必须能被服务端读出来算 HMAC，加密存放只是把密钥
> 从"数据库"挪到"配置文件"。真正的边界是数据库访问权限——与密码哈希区别在于密码
> 永远不需要还原，所以那里用 bcrypt。恢复码则是**只需要比对**，因此存哈希。

## 4. 接口

### 4.1 登录（公开）

```
POST /api/v1/auth/login
{ "username": "admin", "password": "..." }

# 未启用两步验证：与原来一致，直接返回 access_token / refresh_token
# 已启用：不下发令牌，只给挑战票据
{
  "code": 0,
  "data": {
    "totp_required": true,
    "totp_ticket": "8f3c...",
    "user": { "id": 1, "username": "admin", "role": "admin" }
  }
}
```

```
POST /api/v1/auth/login/totp
{ "ticket": "8f3c...", "code": "123456" }   # code 也可以是 10 位恢复码
```

票据存在 Redis，有效期 5 分钟，**一次一用**；同一张票据累计错 5 次立即作废，
避免拿票据把 6 位口令暴力跑一遍（100 万种组合在无限制接口下并不安全）。

> 降级路径：Redis 不可用时票据无处安放，此时允许在 `POST /auth/login` 里直接带
> `totp_code` 一步完成校验，避免"启用了两步验证 + Redis 故障 = 永远进不去后台"。

### 4.2 自助管理（管理员，登录后）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/security/totp` | 状态：是否启用、启用时间、恢复码余量、账号名 |
| POST | `/admin/security/totp/setup` | 生成新密钥，返回 `secret` 与 `otpauth://` 链接（此时**尚未生效**） |
| POST | `/admin/security/totp/enable` | `{code}` 校验通过后正式启用，并一次性返回 10 枚恢复码 |
| POST | `/admin/security/totp/disable` | `{password, code}` 同时校验密码与口令，防会话被劫持后一键关闭 |
| POST | `/admin/security/totp/recovery-codes` | `{code}` 换一批恢复码，旧码全部作废 |

### 4.3 兜底（仅内置超级管理员 `admin`）

```
POST /api/v1/admin/users/:id/totp/reset
```

用于"换手机 / 验证器被删 / 恢复码也用完"。只对 `role=admin` 的账号生效，
并写审计日志 `admin.totp_reset`。

## 5. 登录时序

```
浏览器                        API                        Redis / DB
  │  POST /auth/login            │                            │
  │  (username + password)       │── 校验 bcrypt ─────────────▶│
  │                              │── 已启用 TOTP ? ───────────▶│
  │◀── totp_required + ticket ───│── SET ticket(5min) ───────▶│
  │                              │                            │
  │  POST /auth/login/totp       │                            │
  │  (ticket + 6 位码)           │── GET ticket ─────────────▶│
  │                              │── 校验 HMAC 与 last_step ──▶│
  │                              │── DEL ticket（一票一用）───▶│
  │◀── access + refresh token ───│── 轮换 session_key ───────▶│
```

管理员仍是**单会话**：第二步通过后同样会轮换 `session_key` 并吊销旧的刷新令牌，
所以两步验证不会削弱原有的"另一台设备登录即踢下线"行为。

## 6. 安全细节

- **口令重放**：`totp_last_step` 记录已用时间步，同一窗口内二次提交直接拒绝；
  落库用条件更新（`totp_last_step < $1`），并发提交也不会重复通过。
- **时钟偏差**：校验窗口前后各 1 步（±30 秒），并在错误提示里明确提示"检查手机时间"，
  这是实际使用中最常见的失败原因。
- **失败计数**：第二因子错误计入 `users.login_fail_count`，连续 10 次锁定 15 分钟；
  同时计入按 IP + 账号的 Redis 登录限流（10 分钟窗口）。
- **恢复码**：10 枚、一次一用、只存 sha256；生成与核销都在事务里完成。
- **越权**：`/admin/security/*` 不挂模块权限——能不能改自己的安全设置，不应取决于
  别人给你配的业务模块权限；重置他人则用 `isSuperAdmin` 二次校验。
- **审计**：启用 / 关闭 / 重发恢复码 / 超级管理员重置 / 用恢复码登录，均写 `audit_logs`。

## 7. 部署

无需新增依赖，也不需要服务器装 `oathtool` / `pam`：

```bash
# 1. 应用迁移（老库）
bash scripts/migrate.sh

# 2. 重建 api 与 nginx（前端静态文件在 nginx 镜像里）
docker compose --profile app build api-blue nginx
docker compose --profile app up -d api-blue nginx
```

Redis 必须可用：挑战票据、失败计数都依赖它（部署包默认就带 `patnest-redis`）。

## 8. 使用流程

1. 登录后台 → 左侧「系统 → 账号安全」→ **开始绑定**
2. 用验证器 App 扫二维码（或手动输入 32 位密钥）
3. 输入 App 显示的 6 位码 → **启用**
4. 弹窗展示 10 枚恢复码，**当场保存**（关闭后不再显示，只能重新生成）
5. 下次登录：密码 → 动态口令

验证器丢了：登录页点「验证器不在身边？用恢复码」；恢复码也用完，找 `admin`
在「用户管理 → 重置两步验证」。

## 9. 已知限制

- 只覆盖**管理后台**。主人端 / 机构端（App、小程序）未开放两步验证，因为它们的账号
  体系是手机号 + 验证码注册，强制 TOTP 会显著提高普通用户的流失率。
- 密钥在数据库里是明文，数据库失守即等于两步验证失效；如需更强保证，
  可改为用环境变量派生的 AES-GCM 加密存储（代价是环境变量变更后需要重绑）。
- 未提供"强制所有管理员启用"的开关。当前是自助式：谁需要谁绑。
