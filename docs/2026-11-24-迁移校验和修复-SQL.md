# 迁移校验和修复说明（2026-11-24）

## 问题根因

`release-api.sh` 在 migrate 阶段失败：

```
0024  校验不一致   已应用迁移内容被修改，请新增迁移文件而不是改历史文件
0025  校验不一致
0026  校验不一致
0027  已执行        1.017s
```

经线上实查 `schema_migrations` 表确认，**并非内容被篡改，而是 Windows CRLF 换行符导致文件字节变化**：

迁移工具 `internal/migrate/migrate.go` 对 `.sql` 文件的**原始字节**做 SHA-256。本机 `core.autocrlf=true`，`build.ps1` 用 `Copy-Item` 原样复制，把 CRLF 带进发布包；而历史库记录的是 LF 版校验和。哈希口径对照：

| 版本 | 数据库记录 | 历史 LF（应匹配） | 本次 CRLF（不匹配） |
|---|---|---|---|
| 0024 | `495bcc536fdf3bc93da8c7056ca08a8c89d6a914e29dc7c46db5d2c510f428f6` | ✅ 一致 | `011ae6c9154b262f088512b8ff5c010230ffeb75a00c52e04e6229b984f9403e` ❌ |
| 0025 | `4005b0885024242663e99830722b1703cf2aceabdd11eb0424907159b07aa452` | ✅ 一致 | `118e882b1843ae431201b8197885e374c1890935078c9e6d93f9a3caee301204` ❌ |
| 0026 | `9e41750f82e206ed84f987a03b7d042974bff21ace82f8228aa36777c5750124` | ✅ 一致 | `f37b98048accd0146cd10f4e4b6b6422875ecfe9b4044b6ef7fbdcde75004e4d` ❌ |
| 0027 | `76a3f5e246480ebede60bcc7e0262f4f0459f04debd2de81c8ae656dc352c432` | `56daff1731ca570d958a18ccb819c0033f45e0e8732a09e2f40cc00fac09cb2d` | ✅ 首次执行写的是 CRLF 版 |

说明：0024-0026 库内记录是 LF 版，发布包是 CRLF 版 → 失配；0027 本次首次执行，把 CRLF 版校验和写进了库。

## 已做的治本改造

1. `server/patnestServer/internal/migrate/migrate.go`
   - 校验时同时接受「原始字节」与「LF 归一化」两种 sha256，任一匹配即视为内容一致。
   - 新迁移入库统一写 LF 版校验和，口径全局统一。
   - 新增 `TestChecksumPairIgnoresCRLF` 回归测试（已通过）。
2. `build.ps1` 打包时把所有 `.sql` 归一化为 LF，保证跨平台构建确定性。
3. 本 SQL：把库内 0027 的 CRLF 版校验和统一为 LF 版（0024-0026 无需改动）。

## 立即恢复：数据库对齐 SQL（任选其一）

> 前提：新的 `patnest-migrate` 二进制尚未部署前，可先用本 SQL 让**旧二进制**通过校验；部署新二进制后则不再需要。

在存储机 `zdz1.linkzdsada.dpdns.org` 的 `patnest_db` 执行：

```sql
-- 仅修正 0027 一条：CRLF 版 -> LF 版，与前序迁移口径统一
UPDATE schema_migrations
SET checksum = '56daff1731ca570d958a18ccb819c0033f45e0e8732a09e2f40cc00fac09cb2d'
WHERE version = '0027'
  AND checksum = '76a3f5e246480ebede60bcc7e0262f4f0459f04debd2de81c8ae656dc352c432';

-- 核对结果
SELECT version, checksum FROM schema_migrations
WHERE version IN ('0024','0025','0026','0027') ORDER BY version;
```

执行后重新 `release-api.sh 2.1.10` 即可通过（此时库里全为 LF 版，与 LF 化后的发布包字节一致）。

> 注意：0027 的 SQL 本次**已经执行成功**（建验证码表等），不要重复执行其 DDL，只更新校验和记录即可。

## 推荐发布顺序

1. 在存储机执行上面的对齐 SQL（让旧 migrate 也能过）。
2. 用改好的 `build.ps1` 重新打包发布（包内 SQL 已是 LF，且新 migrate 双兼容）。
3. 重新执行 `release-api.sh 2.1.10`。
4. 发布后 `go test ./...` 与 `/health` 回归。
