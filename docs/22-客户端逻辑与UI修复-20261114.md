## 六、追加修复：取消/拒单后同一只宠物仍无法下单（2026-11-14）

### 现象
小程序里订单已取消（或机构已拒单），重新为同一只宠物预约时，下单页仍提示「以下宠物在所选日期已被预订」，提交按钮点不动。

### 定位过程（线上库实查）
以机构 3 的两只宠物为例，`orders` 里实际只有 `completed` 与 `rejected`，没有任何 `cancelled`：

| 订单 | 状态 | 日期 | 宠物 |
| --- | --- | --- | --- |
| 2 | completed | 11-11 ~ 11-18 | 3 |
| 3 | completed | 11-14 ~ 11-17 | 3 |
| 4 | rejected | 11-13 ~ 11-29 | 3 |
| 5 | completed | 11-13 ~ 12-16 | 4 |
| 6 | completed | 11-14 ~ 11-23 | 4 |

用户看到的「已取消」，在库里其实是**机构拒单（rejected）**；而真正把日期占住的是**提前完成的订单**——`completed` 但 `end_date` 还在未来。

### 根因
前端 `pages/order/create.vue` 的冲突预检只排除了 `cancelled` / `rejected`，把 `completed` / `evaluated` 也当成占用档期。
后端 `CreateOrder`（`order_handler.go:86-92`）只统计
`pending_pay / confirmed / accepted / staying`
四种状态，`completed` 不参与冲突判断。于是出现「服务端会放行、客户端自己拦死」的口径分叉。

### 修复
1. `conflicts` 改为**白名单**：只有 `ACTIVE_STAY_STATUS`（pending_pay/confirmed/accepted/staying）才视为冲突，与后端完全一致。
2. 新增 `refreshAvailability()`：`onShow` 非首次返回时重拉所选宠物的寄养记录与机构容量。取消、拒单、完成都会释放资源，页面不能拿着进页面那一刻的旧数据继续判冲突。
3. 用 `shownOnce` 区分「首次进入」与「从订单页返回」，避免首屏重复请求。

### 顺带发现的容量台账偏差（未自动修）
未来 4 天存在 `used` 与有效订单不符（容量 30，暂不影响下单）：

| 日期 | 台账 used | 按有效订单应为 |
| --- | --- | --- |
| 2026-12-01 | 2 | 0 |
| 2026-12-02 | 2 | 0 |
| 2026-12-05 | 1 | 0 |
| 2026-12-06 | 1 | 0 |

这是 2.0.0 部署前遗留的历史账目（0015 已给出重算口径，但只在迁移时执行过一次）。若后续换上容量较小的机构（如容量 1~5），这些残留会把日期误判成满员。可按 0015 的口径重算一次：

```sql
UPDATE sitter_daily_capacity c
SET used = sub.cnt, updated_at = now()
FROM (
  SELECT s.id AS sitter_id, d::date AS cap_date,
         COALESCE((SELECT SUM(o.pet_count) FROM orders o
                   WHERE o.sitter_id = s.id AND o.deleted_at IS NULL
                     AND o.status IN ('pending_pay','confirmed','accepted','staying')
                     AND o.start_date <= d::date AND o.end_date > d::date), 0) AS cnt
  FROM sitters s
  CROSS JOIN generate_series(CURRENT_DATE, CURRENT_DATE + 120, interval '1 day') d
) sub
WHERE c.sitter_id = sub.sitter_id AND c.cap_date = sub.cap_date AND c.used <> sub.cnt;
```
