| 端 | 调用点 | 命中 | 不匹配 |
| --- | --- | --- | --- |
| 管理后台 webadmin | 99 | 99 | 0 |
| 微信小程序 uniapp | 64 | 64 | 0 |
| APP（KMP） | 90 | 90 | 0 |
| **合计** | **253** | **253** | **0** |

字段级校验：把 KMP `ApiModels.kt` 中所有 `@SerialName` 与后端 `json` tag + `gin.H` 的 map 键合并比对，109 个字段全部命中。这一步能提前发现"字段名写错、序列化静默取默认值"这类上线后才暴露的问题。

反向检查：后端有 15 条路由三端未直接调用，均为设计如此（`/geo/tile` 供瓦片代理、`/payments/recharge/notify/:channel` 供支付网关回调、`/pet-owner/sitters*` 新旧两套浏览入口保留兼容等）。

## 四、发现的问题

### P1 · 数据库与应用跨区域，接口普遍 1.5~3 秒

- **现象**：管理后台任意列表页从客户端访问耗时 1.5~3s；服务端本地压测同样偏慢。
- **实测数据**（nginx 容器内直连，排除公网因素）：
  | 接口 | 耗时 | 是否查库 |
  | --- | --- | --- |
  | `/api/v1/version` | 12 ms | 否 |
  | `/swagger.json` | 17 ms | 否 |
  | `/api/v1/sitters` | 426 ms | 是 |
  | `/health`（db+minio+redis 三项） | 499 ms | 是 |
- **根因**：应用服务器在洛杉矶（`64.83.12.91`），PostgreSQL 在国内阿里云（`39.104.86.4`），**跨洋 RTT 168 ms**。业务处理器普遍串行执行 3~10 次查询，单请求累计 400~500ms；叠加客户端到服务器的公网 RTT，页面整体落在 1.5~3s。
- **影响**：功能不受影响，但交互明显发钝，答辩演示时体感差。
- **建议**（按性价比排序）：
  1. 把 PostgreSQL 迁到与 API 同一区域（收益最大，可直接降到几十毫秒）；
  2. 短期内给高频列表接口加 Redis 缓存（项目已有缓存层）；
  3. 合并处理器内的串行查询（如 count + list 合并为窗口函数一次取回）。

### P2 · 未知路由返回 404 空响应体

- **现象**：`GET /api/v1/nope` 返回 `404`，`Content-Length: 0`，**没有** `{code,message}` 信封。
- **影响**：三端当前调用路径全部正确，暂不触发。若后续新增页面写错路径，前端的统一响应拦截器可能拿到空 body 后抛 `Cannot read property 'code' of undefined`，掩盖真实错误。
- **建议**：注册 `NoRoute` 返回 `404 / 30001 / "接口不存在"`，与其余错误口径一致。

### P3 · 商家端"未建机构"时的响应口径不统一

- 大部分 `/sitter/*` 返回 `404 机构资料不存在`；
- 但 `/sitter/orders/manage`、`/sitter/notifications` 返回 `200` + 空列表。
- **影响**：前端要么按 404 引导"去建机构"，要么按空列表展示，两种判断混用会漏掉引导。
- **建议**：统一为 404，或统一为 200 空列表并在文档中写明。

### P4 · 下单接口返回 `order_id`，其余接口用 `id`

- `POST /pet-owner/orders` 返回 `{order_id, order_no, total_amount...}`；列表与详情用的是 `id`。
- **现状**：KMP 与 uniapp 都正确读取了 `order_id`，**当前无故障**。
- **风险**：新增端或重构时极易误读成 `id` 拿到 0，进而跳转到错误详情页。
- **建议**：在接口文档里对该字段加粗标注，或补充返回 `id` 作为别名。

### P5 · 缺少常见安全响应头（低）

- 响应头中没有 `X-Content-Type-Options`、`X-Frame-Options`、`Strict-Transport-Security`。
- **建议**：在 nginx `locations.conf` 的 `add_header` 里补齐，一行即可。

## 五、顺带确认的已生效能力

- **Let's Encrypt 证书已生效**：`issuer=C=US, O=Let's Encrypt, CN=YE1`，`subject=CN=www.linkzdsada.dpdns.org`，有效期至 **2027-02-10**。`curl` 不加 `-k` 也能通过严格校验（退出码 0），说明浏览器不再报证书不受信。
- **9200 端口 http/https 共存**：`http://...:9200/health` 与 `https://...:9200/health` 均返回 200，stream + ssl_preread 分流工作正常。
- **gzip 生效**：主 JS 837 KB 压缩后传输 311 KB（-63%），CSS 363 KB → 68 KB（-81%）。
- **CORS 策略正确**：无 Origin 的客户端（小程序、桌面端、服务端）拿到 `*`；白名单外的 Origin 不回 CORS 头（浏览器侧自然拦截），符合"用 Bearer 不用 Cookie"的设计。
- **错误信封统一**：坏 JSON 返回 `400 / 10001 / 请求参数无效: ...`，与业务错误同一格式。
- **静态资源缓存**：`Cache-Control: public, max-age=31536000, immutable` + ETag，指纹文件名匹配，回访无需重下。
