# PatNest 部署与热更新方案

> 当前交付形态是容器包（Nginx + Redis + Go API），构建与发布操作见
> 《05-编译打包发布运行.md》。本文保留蓝绿切换、在线迁移与发布门禁的设计原理，
> 以及不用容器时的 systemd 部署方式，两者思路一致。

本文说明后端服务、数据库和管理面板如何在不中断用户访问的前提下完成更新，
包括发布流程、回滚方式、数据库变更规范和验收步骤。

## 1 目标与边界

热更新在这套系统里指三层能力：

| 层 | 更新方式 | 用户感受 |
| --- | --- | --- |
| 管理面板 | 新静态目录就位后原子切换软链接 + Nginx reload | 无需停机，已打开页面提示“发现新版本” |
| 后端 API | 蓝绿双实例：新槽位启动并通过健康检查后切流量 | 请求不中断，无 502 |
| 数据库 | 版本化增量迁移，发布前自动执行 | 连接不中断，旧代码仍可读新结构 |

明确不做的部分：

- 管理端提供受控更新入口：上传和扫描只写 `data/updates`，真正的文件替换与发布由宿主机更新代理执行；
  API 容器不挂载 Docker socket，也不直接执行任意命令。
- 不能只改 JWT 密钥、数据库账号、MinIO 密钥而不重启进程；这类配置变化通过“无损重启”生效（见 3.4）。
- 已执行的迁移不允许修改或自动回滚，修正方式是新增一个迁移文件。

## 2 部署拓扑

```
                   公网
                    │
        ┌───────────▼────────────┐
        │ 后端机                  │
        │ Nginx :80/:443          │
        │  ├─ /            → /opt/patnest/web/current（管理面板）
        │  └─ /api,/health → upstream patnest_api
        │        ├─ blue  :9200   （systemd patnest-api@blue）
        │        └─ green :9201   （systemd patnest-api@green）
        └───────────┬────────────┘
                    │ 公网
        ┌───────────▼────────────┐
        │ 存储机                  │
        │ PostgreSQL 18 :5432     │
        │ MinIO :9000             │
        └────────────────────────┘
```

两个槽位运行同一份代码、共用同一个数据库，任一时刻只有一个槽位接流量。
对外端口始终只有 Nginx，9200/9201 只监听本机。

## 3 后端热更新

### 3.1 发布流程

`deploy/scripts/deploy-backend.sh` 按以下顺序执行，任一步失败都会自动恢复原槽位：

1. 读取 `/etc/nginx/patnest/upstream.conf`，判断当前活动槽位，目标为另一个槽位。
2. 用固定版本号编译 `patnest-api` 与 `patnest-migrate`，通过 `-ldflags` 写入版本、提交号、构建时间。
3. 执行数据库增量迁移（`SKIP_MIGRATE=1` 可跳过）。
4. 原子更新 `/opt/patnest/api/current` 软链接，`systemctl restart patnest-api@<目标槽位>`。
5. 轮询 `http://127.0.0.1:<目标端口>/health`，要求返回 200 且 `db=true`，最多 30 秒。
6. 校验 `nginx -t` 后改写 upstream 文件并 `systemctl reload nginx`，新请求进入新槽位。
7. 等待 8 秒排空连接，停止旧槽位；旧槽位进程按 SIGTERM 优雅退出，最多等待 20 秒在途请求。
8. 写入 `system_release` 发布记录，清理超出保留数量的历史版本。

失败时的行为：

- 新实例起不来或健康检查失败：流量从未切换，脚本停掉新槽位并退出。
- `nginx -t` 失败：upstream 文件回写为原端口，旧槽位继续服务。

### 3.2 健康门禁

`GET /health` 返回：

```json
{
  "status": "ok",
  "service": "patnest-api",
  "version": "2026.10.30.101500",
  "commit": "f79173c",
  "slot": "green",
  "db": true,
  "minio": true,
  "uptime_seconds": 12
}
```

- 数据库不可用时返回 `503`，`status` 为 `degraded`，脚本不会把流量切过去。
- MinIO 异常只标记 `minio=false`，不影响接流量，但上传功能不可用。
- `/health` 不鉴权、不写日志，便于 Nginx 与脚本高频探测。

### 3.3 启动韧性

`cmd/api` 启动时对数据库连接做 15 次、每次间隔 2 秒的重试。发布窗口内数据库切换或迁移
导致连接失败时，新实例会等待而不是直接退出，避免蓝绿流程误判。

### 3.4 配置变更

`.env` 与 `shared/slot.<槽位>` 由 systemd 在进程启动时读取。修改配置后执行：

```bash
source deploy/.env
SKIP_MIGRATE=1 bash deploy/scripts/deploy-backend.sh
```

脚本会完成一次“构建 + 双槽位滚动”，配置在用户无感知的情况下生效。
只改端口、账号、密钥等配置时，也可在单个槽位执行 `systemctl restart patnest-api@blue`，
但会产生秒级抖动，生产环境推荐走脚本。

## 4 数据库在线迁移

### 4.1 迁移工具

`cmd/migrate` 负责执行 `serverdb/migrations/*.sql`：

```bash
cd server/patnestServer
go run ./cmd/migrate -status              # 查看状态
go run ./cmd/migrate -dry-run             # 只列出待执行项
go run ./cmd/migrate                      # 执行
```

容器部署使用包内 `scripts/migrate.sh`，它通过 compose 的 `migrate` 一次性服务执行。

### 4.2 机制

| 机制 | 说明 |
| --- | --- |
| 版本表 | `schema_migrations(version, name, checksum, applied_at, execution_ms)` |
| 顺序 | 按文件名数字前缀升序执行，版本号重复直接报错 |
| 事务 | 每个文件在独立事务中执行，失败整体回滚 |
| 并发 | 持有 `pg_advisory_lock`，多个发布任务不会重复执行 |
| 校验和 | 已应用文件被改动时拒绝执行，提示新增迁移而不是改历史 |
| 免事务迁移 | 文件首行写 `-- migrate:no-transaction`，用于 `CREATE INDEX CONCURRENTLY` 这类不能进事务的语句 |

`0001_baseline.sql` 是占位基线（内容只有 `SELECT 1;`），用于把 `init.sql` 建立的结构纳入版本管理，
**其内容与校验和不得改动**（老库依赖它做校验和比对）。

2026-11-09 起，`init.sql` 已合并原 `0001`~`0021` 的**全部净效果**：**全新库只执行 `init.sql` 即可**，
文件内会预建 `schema_migrations` 表并写入 `0001` 记录，之后再跑 `cmd/migrate` 是幂等空操作。
脚本本身也是**可重复执行**的：建表/索引/视图/函数幂等，触发器先 `DROP IF EXISTS` 再建，种子数据按唯一键判重，
因此重跑不会报错也不会产生重复行，可以拿来修复“跑到一半失败”留下的半成品库。

```bash
# Linux / macOS
PGCLIENTENCODING=UTF8 psql -v ON_ERROR_STOP=1 -U postgres -d patnest_db -f serverdb/init.sql
```

```powershell
# Windows（先设客户端编码，避免中文注释在 GBK 下报 invalid byte sequence）
$env:PGCLIENTENCODING = "UTF8"
psql -v ON_ERROR_STOP=1 -U postgres -d patnest_db -f serverdb\init.sql
```

`SET client_encoding = 'UTF8'` 放在文件第一条语句、且文件不带 BOM —— 这两点是 Windows 上能跑通的前提，不要调换顺序。
历史脚本归档在 `migrations/archive/`（迁移器只读主目录、跳过子目录，不会再加载它们）。
**老库无需改动**：迁移器只看到 `0001` 且校验和一致，`schema_migrations` 里多余的 `0002`~`0021`
记录不会被检查，也不会报错。今后新的结构变更从 `0022` 起新增脚本，并同步体现到 `init.sql`。

免事务迁移没有自动回滚保护，因此必须写成可重复执行的语句（`IF NOT EXISTS`、
`OR REPLACE`），一次文件只做一件事，失败时人工确认后再补一个迁移修正。

### 4.3 零停机变更规范

发布期间新旧代码会同时读库，迁移必须遵循“扩展 - 收缩”：

1. **扩展**：只做加法。新增可空列、新增表、新增索引（大表用 `CREATE INDEX CONCURRENTLY`）、
   新增枚举值。旧代码不认识新字段也能正常运行。
2. **双写/回填**：新代码同时写新旧结构，后台分批回填历史数据。
3. **收缩**：确认全部实例升级完成、观察一个发布周期后，再删除旧列或收紧约束。

禁止在同一个发布里既改代码又删除旧列；禁止 `ALTER COLUMN ... TYPE` 直接改大表类型；
禁止在迁移里执行长时间 `UPDATE` 全表（放到独立的数据修复脚本，分批提交）。

### 4.4 发布记录

`0002_system_release.sql` 建立 `system_release` 表，脚本在发布成功后写入一条记录，
后台“经营看板 - 系统与发布信息”可直接看到最近五次发布。

### 4.5 发布期间的一致性保障

热更新期间数据库不是“锁住不让访问”，而是靠下面的顺序把风险收敛：

| 阶段 | 数据库状态 | 保障手段 |
| --- | --- | --- |
| 迁移执行 | 旧实例仍在服务 | 迁移只做加法，旧代码不认识的列/表可忽略 |
| 迁移失败 | 未提交，结构不变 | 单文件事务回滚；脚本立即退出，upstream 不动 |
| 新实例启动 | 新旧结构并存 | 新代码只读新结构，且保留对旧字段的兼容读取 |
| 健康检查 | 新实例已连库 | `/health` 要求 `db=true`，连不上就不切流量 |
| 切流量后 | 双实例短暂并存 | 代码必须同时兼容新旧结构，直到旧实例停止 |
| 旧实例停止 | 只剩新结构使用者 | 下一个版本才可以删除旧列 |

关键约束：**同一个版本里不能既改代码又删除旧结构**。删除动作必须延后到下一版本，
否则在切流量前旧实例会读到已删除的列而报错。

### 4.6 常见变更写法

新增字段（旧代码无感知）：

```sql
ALTER TABLE orders ADD COLUMN IF NOT EXISTS channel VARCHAR(32);
```

新增索引（不锁表，需免事务标记）：

```sql
-- migrate:no-transaction
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_channel ON orders (channel);
```

重命名字段（拆成三个版本）：

1. 新增新列，代码双写新旧列；
2. 分批回填历史数据（`UPDATE ... WHERE id BETWEEN ...`，每批单独提交）；
3. 确认全部实例使用新列后，下一版本删除旧列。

调整枚举（先加值，再使用）：

```sql
ALTER TYPE order_status ADD VALUE IF NOT EXISTS 'refunding';
```

`ALTER TYPE ... ADD VALUE` 在部分 PostgreSQL 版本中不能在事务块内执行，
若迁移报错，给该文件加上 `-- migrate:no-transaction`。

## 5 管理面板热更新

### 5.1 原子切换

`deploy/scripts/deploy-web.sh`：

1. 把 `dist/` 完整复制到 `/opt/patnest/web/releases/<时间戳>/`。
2. 用 `ln -sfn` + `mv -Tf` 原子替换 `current` 软链接，不存在“半个版本”的中间态。
3. `nginx -t` 通过后 `systemctl reload nginx`，旧进程处理完在途请求后退出。
4. 保留最近 5 个版本，供 `rollback.sh` 使用。

### 5.2 缓存策略

| 路径 | 缓存 | 原因 |
| --- | --- | --- |
| `/index.html` | `no-cache` | 入口必须每次校验，保证新版本立即生效 |
| `/assets/*` | `max-age=31536000, immutable` | 文件名带内容哈希，可长期缓存 |
| `/version.json` | `no-store` | 版本探测必须实时 |

### 5.3 前端感知新版本

构建时 `vite.config.js` 注入 `__APP_BUILD_ID__`，并在产物根目录生成 `version.json`：

```json
{
  "version": "1.0.0",
  "commit": "f79173c",
  "build_time": "2026-10-30T02:01:51.831Z",
  "build_id": "1.0.0.f79173c.20261030020151"
}
```

管理面板每 60 秒请求一次 `version.json`，`build_id` 与当前运行版本不一致时，
顶栏出现“发现新版本”，点击后整页刷新；用户正在填写的表单不会被强制打断。

### 5.4 管理端更新入口

容器包在 `data/updates` 下划出以下目录：

| 目录 | 用途 |
| --- | --- |
| `tmp/` | 管理页面“上传更新包”写入的 zip（宿主机临时目录，同目录下旧版 `inbox/` 仍会被扫描） |
| `manual/` | 运维人员手工放进去的 zip |
| `queue/` | 管理端点击“应用更新”后生成的任务 |
| `processing/` | 更新代理正在执行的任务 |
| `failed/` | 执行失败的任务 |
| `status/` | 更新代理回写的任务状态 |
| `staging/` | 通过校验后解压出来的待发布文件 |
| `backups/` | 每次更新前的文件备份 |
| `logs/` | 每个任务的发布日志，页面可查看 |

流程：

1. 管理员在“系统更新”页上传 zip（落到 `data/updates/tmp`），
   或把 zip 放到服务器上的 `data/updates/manual`，然后在页面点击“检查更新”；
2. API 校验 zip 结构、版本号和允许的文件，写入 `queue/<job>.job`；
3. 更新代理认领任务并备份当前文件。Linux 默认跑 `update-agent` 容器（`agent` profile）；
   Windows / Podman / 显式 `AGENT_MODE=host` 时跑宿主机 `update-agent.ps1` / `update-agent.sh`；
4. 代理调用现有 `release-api` / `release-web` 脚本，蓝绿切换成功后写 `success`；
5. 失败时恢复备份文件，任务标为 `failed`，旧槽位继续接流量。

代理与 API 的边界是刻意设计的：即使后台账号被盗，也只能提交更新包，不能在 API 容器里
获得宿主机 Docker 控制权。**更新代理是唯一被授权操作容器引擎的组件**：`host` 模式下该权限
属于宿主机上的代理进程，`container` 模式下通过挂载 `docker.sock` 交给代理容器（等价于
宿主机级权限，安全权衡见 `deploy/docker/README.md`）。更新包仍然只允许替换
`artifacts/`、`web/dist/` 与 `db/migrations/`，不会覆盖 compose、Nginx 配置或脚本。

容器模式要求部署包以**宿主机相同的绝对路径**挂进代理容器（`.env` 的 `PACKAGE_ROOT`，
由 `install.sh` 自动写入）。因为发布动作是代理在容器内执行 `docker compose build`，
build context 路径最终由宿主机 daemon 解析；两边路径不一致会找不到 Dockerfile，
或把蓝绿槽位误判成另一套 compose 项目。移动部署目录后须重跑 `install.sh` 刷新该值。

## 6 版本与观测

| 接口 | 鉴权 | 用途 |
| --- | --- | --- |
| `GET /health` | 无 | 蓝绿健康门禁、监控探活 |
| `GET /api/v1/version` | 无 | 版本、提交、槽位、启动时间、运行时长 |
| `GET /api/v1/admin/system/info` | 管理员 | 后端版本、数据库版本与迁移状态、MinIO 状态、最近发布记录 |

看板底部的“系统与发布信息”即为上述数据的可视化展示，可用于答辩演示热更新结果。

## 7 操作手册

### 7.1 首次部署

1. 存储机执行 `serverdb/init.sql` 建库（一次完成全部 35 张业务表、函数、触发器、视图与种子数据；已含原 `0001`~`0021` 净效果），创建后端使用的数据库账号。
2. 后端机安装 Nginx、Go、psql，创建 `patnest` 用户及 `/opt/patnest/{api,web}` 目录。
3. 安装 `deploy/systemd/patnest-api@.service`、`deploy/nginx/patnest.conf`，
   准备 `/etc/nginx/patnest/upstream.conf`。
4. 写入 `/opt/patnest/api/shared/.env`、`slot.blue`、`slot.green`。
5. `source deploy/.env` 后依次执行 `deploy-backend.sh`、`deploy-web.sh`。
6. 访问 `http://<后端机>/health` 与后台登录页确认。

### 7.2 日常发布

```bash
source deploy/.env
bash deploy/scripts/deploy-backend.sh   # 含迁移与蓝绿切换
bash deploy/scripts/deploy-web.sh       # 管理面板
```

### 7.3 回滚

```bash
bash deploy/scripts/rollback.sh            # 回到上一个后端版本
bash deploy/scripts/rollback.sh 2026.10.29.220000
```

管理面板回滚同样是把 `current` 指回旧目录：

```bash
ln -sfn /opt/patnest/web/releases/<旧版本> /opt/patnest/web/current.tmp
mv -Tf /opt/patnest/web/current.tmp /opt/patnest/web/current
systemctl reload nginx
```

### 7.4 常见问题

| 现象 | 排查 |
| --- | --- |
| 发布卡在健康检查 | `journalctl -u patnest-api@green -n 100`，重点看数据库连接与 MinIO |
| 切换后出现 502 | 检查 `upstream.conf` 端口与 `slot.<槽位>` 中 `APP_PORT` 是否一致 |
| 管理面板看不到更新提示 | 确认 `version.json` 未被缓存、`current` 已指向新目录 |
| 迁移报校验不一致 | 不要回改历史文件，新增一个迁移完成修正 |
| 迁移报锁等待 | 上一轮发布未退出，确认没有残留 `cmd/migrate` 进程 |

截图或演示时，可在发布前后分别访问 `/api/v1/version`，展示 `version` 与 `slot` 变化、
`uptime_seconds` 归零，同时页面无中断。
