**失败详情（缺陷 D-01）**：

```
package patnestServer/internal/swagger
    imports patnestServer/internal/router from swagger_test.go
    imports patnestServer/internal/handler from router.go
    imports patnestServer/internal/swagger from admin_swagger.go: import cycle not allowed in test
FAIL    patnestServer/internal/swagger [setup failed]
```

根因：v2.3.0 新增 Swagger 运行期开关，`internal/handler/admin_swagger.go` 引用了 `internal/swagger`；而 `internal/swagger/swagger_test.go`（包内测试）又引用 `internal/router`，router 再引用 handler，形成 `swagger(test) → router → handler → swagger` 的引用环。

影响：`TestGeneratedSpecCoversRoutes`（防止新增路由漏写文档的覆盖测试）与 `TestDocAndUIEndpoints` 无法运行，Swagger 文档与路由表的防漂移机制失效；**不影响服务端运行时功能**。

修复建议：将 `swagger_test.go` 改为包外测试 `package swagger_test`，仅 import `router` 与 `swagger`，切断"handler 反向引用 swagger"在测试链的闭环；或把路由覆盖测试上移到 `internal/router` 包内执行。

## 六、部署发布实测与故障修复（D-02）

本节记录一次完整的"发布失败 → 根因定位 → 修复 → 重新发布 → 回归"实测过程，全部操作在真实服务器 `www.linkzdsada.dpdns.org`（SSH 直连）上完成。

### 6.1 故障现象

执行 `release-api.sh 2.1.10`，在数据库迁移阶段失败：

```
0024  校验不一致   已应用迁移内容被修改，请新增迁移文件而不是改历史文件
0025  校验不一致
0026  校验不一致
0027  已执行        1.017s
[FAIL] release-api.sh failed
```

### 6.2 根因定位

SSH 直连服务器，用 psql 查询 `schema_migrations` 真实 checksum，与本地发布包文件比对：

| 版本 | 数据库记录 | 发布包字节哈希（CRLF） | LF 归一化哈希 |
|---|---|---|---|
| 0024 | `495bcc53…` | `011ae6c9…`（不符） | `495bcc53…`（相符） |
| 0025 | `4005b088…` | `118e882b…`（不符） | `4005b088…`（相符） |
| 0026 | `9e41750f…` | `f37b9804…`（不符） | `9e41750f…`（相符） |
| 0027 | `76a3f5e2…` | `76a3f5e2…`（相符） | — |

结论：`core.autocrlf=true` 下 build.ps1 用 `Copy-Item` 原样复制 CRLF 换行符的 `.sql`，而迁移工具 `migrate.go` 对文件原始字节做 SHA-256；数据库历史记录的是 LF 版哈希，字节口径不一致导致误判。**这是换行符问题，不是内容被篡改**。0027 因首次执行写入了当前 CRLF 哈希，故能通过。

### 6.3 修复措施（三处）

1. **校验逻辑治本**：`internal/migrate/migrate.go` 新增 `checksumPair()`，校验时同时接受「原始字节」与「LF 归一化」两种哈希，任一匹配即通过；新迁移入库统一写 LF 版哈希。新增回归测试 `TestChecksumPairIgnoresCRLF`，`go test ./internal/migrate` 全通过、gofmt 干净。
2. **打包脚本治本**：`build.ps1` 在复制后把所有 `db/**/*.sql` 统一转成 LF（UTF-8 无 BOM），保证跨平台构建确定性。
3. **数据库对齐**：服务器执行 SQL 把 0027 校验和由 CRLF 版更新为 LF 版，并把服务器上 0027 文件转 LF。修复文档见 `docs/2026-11-24-迁移校验和修复-SQL.md`。

### 6.4 修复验证与重新发布

| 步骤 | 结果 |
| --- | --- |
| `patnest-migrate -status` | 全部「已存在」，`[OK] 状态检查完成`，无 mismatch |
| `release-api.sh 2.1.10` | 迁移全通过 → api-blue 启动 → nginx 配置校验通过 → 流量切至 blue → 旧绿槽停止 → `[release] done: 2.1.10` |
| 发布后 `/health` | 200，`slot=blue`，db/minio/redis 全 true |
| 发布后核心接口 | 机构列表、相似推荐均 200；未登录鉴权正确返回 401 |

### 6.5 遗留事项

服务器上 `artifacts/patnest-api` 为 11-22 旧构建（commit `bc517a2`），不含 `send-code` / `login/code` 路由，故实测仍返回 404。本次仅修复了发布流程，**未替换 API 二进制**。处理方案：用修好的 `build.ps1` 重新打包发布包（自动携带最新 v2.3 二进制 + LF 化 SQL + 双兼容 migrate），上传后重新执行 `release-api.sh`，届时新路由将可用、版本号同步更新。

## 七、测试结论与建议

1. **功能层面**：v2.3.0 经执行人手工实测，全部功能可用、逻辑正常，四端协同与核心业务闭环成立，满足交付与演示要求。
2. **自动化层面**：`go test ./...` 存在 1 项回归缺陷（D-01），属测试代码引用结构问题，不影响运行时，但削弱了 Swagger 文档防漂移能力，建议优先修复。
3. **部署层面**：发布失败（D-02）已定位为换行符导致的校验和误判，三处治本改造 + 数据库对齐后，真实重跑发布脚本成功、服务正常；仅剩 API 二进制待重新打包发布以启用新路由。
4. **性能层面**：接口耗时偏高与跨区域数据库有关，功能无阻塞，按历史 P1 建议优化。

**综合判定：通过（功能）/ 通过（部署修复后）/ 有条件通过（自动化）。**
