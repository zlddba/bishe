# PatNest 编译、打包、发布与运行

本文覆盖从本机编译到服务器运行的完整链路：

```
本机（Windows / Linux）
  build.ps1 / build.sh
        │  构建管理页面 + 交叉编译 Go
        ▼
release/patnest-docker-<版本>.zip
        │  上传到后端服务器
        ▼
服务器
  scripts/install.sh     首次部署（打镜像 + 迁移 + 启动）
  scripts/release-api.sh 后端蓝绿发布
  scripts/release-web.sh 管理页面发布
  scripts/rollback.sh    版本回滚
  scripts/*.ps1          Windows 下的等价脚本
```

存储服务器（PostgreSQL 18 + MinIO）独立运行，不在后端 compose 内。

## 1 环境要求

### 1.1 构建机

| 依赖 | 要求 | 说明 |
| --- | --- | --- |
| Go | 1.25+ | 交叉编译 `linux/amd64` 或 `linux/arm64` 静态二进制 |
| Node.js | 20+ / 22+ | 管理页面构建；有 `node_modules` 时直接调用本地 vite |
| zip | 可选 | 没有时脚本自动退化为 `tar.gz` |
| git | 可选 | 用于把提交号写进版本号，没有则记为 `unknown` |

### 1.2 后端服务器

| 依赖 | 说明 |
| --- | --- |
| podman 或 docker | 运行容器 |
| podman-compose / `podman compose` / `docker compose` | 三者任一，脚本自动识别 |
| bash 或 PowerShell 5.1+ | 执行发布脚本；Linux 用 `.sh`，Windows 用 `.ps1` |
| 端口 | 默认只放行 `9200`（可用 `PUBLIC_PORT` 改） |

服务器不需要安装 Go、Node，也不需要编译源码。

### 1.3 存储服务器

PostgreSQL 18（`:5432`）与 MinIO（`:9000`）需对后端服务器公网 IP 开放，
账号密码写入后端 `.env`。

## 2 发布包结构

构建产物解压后：

```
patnest-docker-1.0.0/
├── compose.yaml              # nginx + redis + api-blue/api-green + migrate
├── .env.example              # 配置模板
├── .dockerignore
├── README.md                 # 服务器侧速查
├── artifacts/
│   ├── patnest-api           # 已编译的 Linux 二进制
│   └── patnest-migrate       # 迁移工具
├── web/dist/                 # 已构建的管理页面（含 version.json）
├── docker/
│   ├── Dockerfile.api        # 只 COPY 二进制，秒级打镜像
│   ├── Dockerfile.web        # 只 COPY dist 到 nginx 镜像
│   └── nginx/default.conf    # 9200：管理页面 + /api 反代
├── nginx/upstream.conf       # 当前活动槽位（blue/green）
├── db/
│   ├── init.sql              # 全量建库（仅首次，在存储服务器执行）
│   └── migrations/           # 增量迁移，发布时自动执行
└── scripts/
    ├── common.sh             # 识别 compose 命令
    ├── install.sh            # 首次部署
    ├── release-api.sh        # 后端蓝绿发布
    ├── release-web.sh        # 管理页面发布
    ├── rollback.sh           # 回滚到指定镜像
    ├── migrate.sh            # 单独执行/查看迁移
    ├── common.ps1            # Windows 公共函数
    ├── install.ps1           # Windows 首次部署
    ├── release-api.ps1       # Windows 后端蓝绿发布
    ├── release-web.ps1       # Windows 管理页面发布
    ├── rollback.ps1          # Windows 版本回滚
    └── migrate.ps1           # Windows 迁移命令
```

## 3 编译与打包

### 3.1 Windows

```powershell
cd D:\schoollearn\biyezuopin
.\build.ps1
```

常用参数：

```powershell
.\build.ps1 -Version 1.1.0          # 指定版本号
.\build.ps1 -Arch arm64             # 构建 ARM 服务器用的二进制
.\build.ps1 -SkipWeb                # 复用已有 dist，只重编后端
.\build.ps1 -SkipGo                 # 复用上次二进制，只重建页面
.\build.ps1 -NoZip                  # 只生成目录，不压缩
```

### 3.2 Linux / macOS

```bash
cd /path/to/biyezuopin
bash build.sh
```

```bash
bash build.sh --version 1.1.0
bash build.sh --arch arm64
bash build.sh --skip-web
bash build.sh --skip-go
bash build.sh --no-zip
```

### 3.3 脚本做了什么

1. 读取版本号（参数优先，否则取 `webadmin/.../package.json` 的 `version`）。
2. 构建管理页面：优先执行本地 `node_modules/.bin/vite build`，没有时回退到 `npm ci && npm run build`。
3. 交叉编译 `patnest-api`、`patnest-migrate`，注入版本、提交号、构建时间。
4. 复制 `deploy/docker` 模板、`web/dist`、`db/`，组成 `release/patnest-docker-<版本>/`。
5. 压缩为 `release/patnest-docker-<版本>.zip`。

构建结果示例：

```
[build] version=1.0.0 commit=f79173c arch=amd64
[build] Building admin panel (vite) ...
[build] Building Go binaries for linux/amd64 ...
[build] Assembling container package ...
[build] Archive: release/patnest-docker-1.0.0.zip (9.6 MB)
```

### 3.4 版本号约定

- 页面版本来自 `package.json`，后端版本通过 `-ldflags` 注入，两者保持一致。
- 发布记录写入数据库 `system_release` 表，可在后台“经营看板 → 系统与发布信息”查看。
- 管理页面每 60 秒对比线上 `version.json`，有新构建时顶栏出现“发现新版本”。

## 4 首次部署

### 4.1 初始化数据库（只做一次）

在存储服务器上执行：

```bash
psql -U postgres -d patnest_db -f db/init.sql
```

`init.sql` 是**唯一的全量基线**：建 35 张业务表、函数、触发器、索引、视图与种子数据，
并预建 `schema_migrations`、写入 `0001` 记录。2026-11-09 已把原 `0001`~`0021` 的净效果全部合并进来，
**新库执行这一条命令即可**，随后再跑 `cmd/migrate` 只是幂等确认（不会重复建表）。

历史迁移脚本归档在 `serverdb/migrations/archive/`，发布包只带主目录的
`0001_baseline.sql`（占位，内容与校验和不得改动）。今后新的结构变更仍从 `0022` 起
新增 `00NN_名字.sql`，**并且必须同步更新 `init.sql`**，让新库与老库结构始终一致；
不要再修改已归档的历史脚本。

### 4.2 上传并配置

```bash
scp release/patnest-docker-1.0.0.zip root@<后端服务器>:/opt/
ssh root@<后端服务器>
cd /opt && unzip patnest-docker-1.0.0.zip && cd patnest-docker-1.0.0
cp .env.example .env
vi .env
```

`.env` 关键字段：

| 变量 | 说明 |
| --- | --- |
| `COMPOSE_PROJECT_NAME` | 固定 `patnest`，保证容器名稳定 |
| `APP_VERSION` | 镜像标签，与包版本一致 |
| `PUBLIC_PORT` | 对外端口，默认 `9200` |
| `JWT_SECRET` | 至少 32 位随机串，泄漏需全部重签 |
| `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD` | 存储服务器数据库 |
| `MINIO_ENDPOINT/ACCESS_KEY/SECRET_KEY/BUCKET/USE_SSL` | 存储服务器对象存储 |
| `REDIS_PASSWORD` | 本机 Redis 密码，必须改掉默认值 |

### 4.3 启动

```bash
bash scripts/install.sh
```

脚本等价于：

```bash
podman-compose --profile app build --pull api-blue nginx
podman-compose --profile tools run --rm migrate
podman-compose --profile app up -d redis nginx api-blue
```

也可以手动执行 `podman-compose --profile app up -d --build`。

### 4.4 Windows 启动

Windows 服务器不需要安装 Bash，直接使用包内同名的 `.ps1` 脚本。前置条件：

- Docker Desktop 已启动，并处于 **Linux containers** 模式；或 Podman Desktop 已初始化；
- `docker compose version` / `podman compose version` 至少一个能正常输出；
- 解压后从包根目录执行命令（脚本会自动切到包根目录，不依赖当前路径）。

```powershell
cd D:\opt\patnest-docker-1.0.0
Copy-Item .env.example .env
notepad .env

Set-ExecutionPolicy -Scope Process Bypass
.\scripts\install.ps1
```

如果公司策略不允许修改执行策略，用单次绕过的方式：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1
```

从浏览器下载的压缩包可能带“来自 Internet”标记，必要时先解除：

```powershell
Get-ChildItem .\scripts\*.ps1 | Unblock-File
```

`install.ps1` 会依次完成：构建 `patnest-api` / `patnest-web` 镜像、执行迁移、
启动 Redis + Nginx + api-blue、轮询 `/health`，最后打印
`db` / `minio` / `redis` 三项连接结果。数据库不可达会直接报错退出；
MinIO 或 Redis 不可达会给出警告，但不会阻止 API 启动。

### 4.5 验收

| 检查项 | 命令/地址 | 期望 |
| --- | --- | --- |
| 容器状态 | `podman-compose --profile app ps` | redis / nginx / api-blue 均为 Up |
| 健康检查 | `curl http://127.0.0.1:9200/health` | `status=ok`、`db=true`、`redis=true` |
| 版本信息 | `curl http://127.0.0.1:9200/api/v1/version` | 返回版本与 `slot` |
| 管理页面 | `http://<公网IP>:9200/` | 登录页正常，静态资源 200 |
| 系统信息 | 后台“经营看板 → 系统与发布信息” | 数据库版本、迁移记录、发布记录齐全 |

`/health` 在数据库不可达时返回 `503`，发布脚本以此作为切流量的门禁。

## 5 日常发布

### 5.1 后端蓝绿发布

1. 本机用 `build.ps1` / `build.sh` 生成新包；
2. 把新的 `artifacts/patnest-api`（以及 `patnest-migrate`）覆盖到服务器包目录；
3. 执行：

```bash
APP_VERSION=1.1.0 bash scripts/release-api.sh
```

Windows：

```powershell
.\scripts\release-api.ps1 -Version 1.1.0
```

脚本流程：

1. 读取 `nginx/upstream.conf` 判断当前槽位，选择另一个槽位；
2. 打新镜像 `patnest-api:<版本>`；
3. 执行增量迁移；
4. 启动备用槽位，轮询 `/health`，最多 30 秒；
5. 健康后改写 upstream 并 `nginx -s reload`；
6. 等待 8 秒排空连接，停止旧槽位。

健康检查失败时不会切流量，脚本会打印新槽位日志并停掉它。

### 5.2 管理页面发布

```bash
# 覆盖 web/dist 后
APP_VERSION=1.1.0 bash scripts/release-web.sh
```

```powershell
# Windows，覆盖 web/dist 后
.\scripts\release-web.ps1 -Version 1.1.0
```

重建 `patnest-web` 镜像并重启 nginx 容器，约 1 秒；已打开的页面轮询到
`version.json` 变化后会提示刷新。

### 5.3 数据库变更

新增 `db/migrations/0003_xxx.sql`，随包发布，`release-api.sh` 会自动执行：

```bash
bash scripts/migrate.sh -status   # 查看状态
bash scripts/migrate.sh -dry-run  # 只列出待执行
```

```powershell
.\scripts\migrate.ps1 -status     # 查看状态
.\scripts\migrate.ps1 -dry-run    # 只列出待执行
```

规范：

- 只增不改：新增可空列、新表、新索引；删除列放在后续版本。
- 大表索引用 `CREATE INDEX CONCURRENTLY`，文件首行加 `-- migrate:no-transaction`（这条语句不能进事务）。
- 已执行的迁移文件不允许修改，校验和不一致会拒绝执行。

发布顺序保证：

1. 迁移先执行，失败则整体回滚且不切流量；
2. 迁移只做加法，仍在服务的旧实例不受影响；
3. 新实例健康检查通过才切换 upstream；
4. 旧实例排空后停止，删除旧结构留到下个版本。

### 5.4 回滚

旧镜像保留在服务器上时：

```bash
bash scripts/rollback.sh 1.0.0
```

```powershell
.\scripts\rollback.ps1 -Version 1.0.0
```

流程与新版本发布一致：启动另一槽位的旧镜像 → 健康检查 → 切 upstream → 停当前槽位。
数据库迁移默认不回滚，回滚代码前确认迁移是向后兼容的（扩展阶段）。

### 5.5 管理端一键更新

管理后台“系统更新”页面提供两条入口：

1. **上传更新包**：选择 `patnest-docker-<版本>.zip`，文件保存到 API 容器的
   `/var/lib/patnest/updates/tmp`，宿主机对应 `data/updates/tmp`。
2. **服务器目录**：把 zip 放到 `<部署目录>/data/updates/manual`，在页面点击
   “检查更新”，列表出现后点击“应用”。

真正执行发布的是更新代理，不是 API 容器。Linux 服务器推荐**容器化**（默认），
Windows / Podman 仍用宿主机脚本；由 `.env` 的 `AGENT_MODE` 选择
（`auto` / `container` / `host` / `none`）。

```bash
# Linux：容器模式（install.sh 会自动完成，下面用于单独重建与查看）
docker compose --profile agent up -d --build update-agent
docker compose --profile agent ps
docker logs -f patnest-update-agent
```

```powershell
# Windows / 宿主机模式：后台隐藏启动，避免关掉窗口就掉线
$agent = (Resolve-Path .\scripts\update-agent.ps1).Path
Start-Process powershell.exe `
  -ArgumentList "-NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File `"$agent`"" `
  -WorkingDirectory (Get-Location).Path -WindowStyle Hidden
```

```bash
# Linux 宿主机模式（AGENT_MODE=host）
nohup bash scripts/update-agent.sh >> data/updates/agent.log 2>&1 &
```

`install.sh` 在 container 模式下会把部署包绝对路径写入 `.env` 的 `PACKAGE_ROOT`，
并以**相同路径**把部署包挂进代理容器：代理在容器内执行 `docker compose build`，
build context 路径最终由宿主机 daemon 解析，两边不一致会找不到 Dockerfile。
该模式会挂载 `docker.sock`（等价于宿主机容器引擎控制权，安全权衡见
`deploy/docker/README.md`）；不接受就设 `AGENT_MODE=host`。移动部署目录后须重跑 `install.sh`。

安装脚本会自动创建
`data/updates/{tmp,manual,queue,processing,failed,status,logs,staging,backups}`，
Windows 还会创建当前用户的启动快捷方式。页面上的“更新代理”显示离线时，
先确认代理容器 / 进程在跑，再看 `data/updates/agent.heartbeat` 是否在 30 秒内更新过。

更新包允许包含：

| 路径 | 作用 |
| --- | --- |
| `artifacts/patnest-api`、`artifacts/patnest-migrate` | 后端二进制 |
| `web/dist/` | 管理页面 |
| `db/migrations/*.sql` | 增量迁移 |
| `update-manifest.json` | 版本、构建时间与文件 SHA256 |

不允许替换 `compose.yaml`、`docker/`、`nginx/`、`scripts/`。更新代理会先备份当前文件；
后端健康检查失败时恢复备份，任务状态写为 `failed`，旧槽位继续服务。

## 6 运行与运维

### 6.1 常用命令

```bash
podman-compose --profile app ps
podman logs -f patnest-api-blue
podman logs -f patnest-nginx
podman exec patnest-redis redis-cli -a '<密码>' ping
podman exec patnest-nginx wget -qO- http://api-blue:9201/health
podman exec patnest-nginx wget -qO- http://127.0.0.1:9200/api/v1/version
```

`podman` 换成 `docker` 即可用于 Docker 环境。容器化更新代理属于独立的 `agent` profile，
要单独带 profile 管理；它内部用 docker CLI 连 `docker.sock` 执行发布，因此只支持
Docker Engine，Podman 环境请用 `AGENT_MODE=host`。

Windows PowerShell：

```powershell
docker compose --profile app ps
docker logs -f patnest-api-blue
docker logs -f patnest-nginx
docker exec patnest-redis redis-cli -a "<密码>" ping
docker exec patnest-nginx wget -qO- http://api-blue:9201/health
docker exec patnest-nginx wget -qO- http://127.0.0.1:9200/api/v1/version

# 容器化更新代理（agent profile）
docker compose --profile agent ps
docker logs -f patnest-update-agent
```

如果本机用的是 Podman，把上面的 `docker` 换成 `podman` 即可。

### 6.2 数据与卷

| 数据 | 位置 | 说明 |
| --- | --- | --- |
| Redis AOF | `./data/redis` | 登录限流计数，丢失不影响业务正确性 |
| 数据库 / MinIO | 存储服务器 | 不在本 compose 内，需单独备份 |

### 6.3 端口与网络

- 对外仅 `PUBLIC_PORT`（默认 9200），由 nginx 容器提供管理页面与 `/api`。
- Go API 监听容器内 `9201`，不映射到宿主机。
- Redis 只在 compose 默认网络内，不映射端口。
- 外部镜像统一使用 `latest`：`alpine:latest`、`nginx:latest`、`redis:latest`。构建命令带 `--pull`，Redis 每次启动按 `pull_policy: always` 拉取；如需完全可复现的部署，应改回固定版本并定期升级。
- `data/updates` 是 API 容器和更新代理（容器或宿主机进程）的共享目录，保存上传包、队列、状态、日志和备份；不要通过 Nginx 暴露该目录。
- 容器化代理额外挂载 `/var/run/docker.sock` 与整个部署包（`PACKAGE_ROOT` 同路径）；前者等价于宿主机容器引擎控制权，见 `deploy/docker/README.md`。

## 7 常见问题

| 现象 | 排查方向 |
| --- | --- |
| `install.sh` 报 compose 命令不存在 | 安装 `podman-compose` 或 `docker compose` |
| PowerShell 提示“禁止运行脚本” | 执行 `Set-ExecutionPolicy -Scope Process Bypass`，或 `powershell -ExecutionPolicy Bypass -File .\scripts\install.ps1` |
| `install.ps1` 报 `No compose command found` | 启动 Docker Desktop / Podman Desktop，确认 `docker compose version` 或 `podman compose version` 可用 |
| 构建时报 `COPY web/dist ... not found` | 发布包解压不完整，或 `.dockerignore` 排除了 `dist`；重新解压完整包 |
| “更新代理”显示离线 | 容器模式看 `docker compose --profile agent ps` 与 `docker logs patnest-update-agent`；宿主机模式看 `data/updates/agent.pid`。心跳超过 `UPDATE_AGENT_STALE_SECONDS`（默认 30 秒）未刷新即判离线 |
| 容器代理启动即退出，提示 `PACKAGE_ROOT` / `docker.sock` | 重跑 `bash scripts/install.sh` 写入真实部署路径；rootless Docker 在 `.env` 设 `DOCKER_SOCKET` |
| 容器内发布报找不到 Dockerfile / 蓝绿槽位变成另一套容器 | `PACKAGE_ROOT` 与宿主机路径不一致（常见于移动部署目录），重跑 `install.sh` |
| 镜像构建卡住 | 检查基础镜像能否拉取；离线环境需提前 `podman load` |
| 健康检查 503 | 数据库不可达或密码错误，看 `podman logs patnest-api-blue` |
| 登录 429 | Redis 限流生效（同 IP + 用户名 10 分钟 5 次），等待或清 key |
| 页面上传图片失败 | MinIO 地址/密钥错误，或存储服务器白名单未放行 |
| 页面打不开但 /health 正常 | 检查 `web/dist` 是否随包发布、nginx 日志 |
| 切流量后 502 | `nginx/upstream.conf` 槽位与运行中的容器不一致 |
| 迁移校验和不一致 | 不要改历史迁移，新增一个修正迁移 |
